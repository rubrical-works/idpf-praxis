# /work Execution Rule — Rationale
**Version:** v0.112.0
**Source:** Reference/work-execution-rationale.md
The reasoning behind decisions `Reference/work-execution.md` (rule 08) directs without re-arguing (#3248). Nothing auto-loads this file; rule 03's On-Demand Documentation Loading table names it for a session questioning a `/work` directive. It ships with every other `Reference/` document and is never registered under `deploymentFiles.rules`. Each section names the rule step it explains.
## Execution Instructions: why the task-tools degradation is announced (#2593)
The task tools may not exist in a session: they are gated by a remote flag (`tengu_rosy_wren`, default off), and because the gate is a server-side rollout, availability can differ between sessions with no local change. Rule 08 calls the task list the runtime step machine and Behavior Rule 5 makes it the resume point; an inline checklist lives in the context window, which is precisely what compaction discards. Announcing the degradation is the load-bearing part: an absent step machine is otherwise indistinguishable from one that was never created, and it surfaces later as work resumed from the wrong step. The startup hook's `Task Tools:` row reports the same condition when it is not enabled locally.
## Phase 2: why the emission shape is stated at the point of use (#2806)
The requirement has always lived in rule `07`; this line previously described a loop, so a session meeting it at the point of use was told to do the thing § Emission rejects. Measured on `/work 2787`: 19 sequential `TaskCreate` calls cost 433ms of tool execution against 55.85s of interval — the cost is per round trip, so one message collapses 19 of them into one.
## Phase 2: why a tree run creates no per-sub-issue step tasks (#3323)
Under an epic or branch tracker, Steps 3 to 5 (and 4f outside `--nonstop`) run once per sub-issue, but Phase 2 used to give each one shared task. One task cannot say which sub-issue's turn of the step is current, so the lifecycle #3176 prescribed for it (in_progress until the last sub-issue) went unfollowed: on `/work 3247 --nonstop` every step ran, yet the shared tasks were never updated and were pruned with no `Not executed:` report. Had compaction struck, `TaskList` would have named Step 3b as the resume point whatever step was current. The per-sub-issue parent tasks were the only accurate signal, so they now carry the step list, and the step inside a sub-issue is re-derived from the evidence each step leaves in the issue body — checked ACs, the `**Doc judgment:**` line, `### Files Changed`, board status — the same evidence the absent-task-tools path relies on. The `Not executed:` report narrows to the tasks that still exist and can go stale.
## Step 1: why test-plan issues redirect, and prd and proposal do not (#2784)
Routing sits beside epic and branch, not inside them — an approval issue's six gates are a checklist `/review-test-plan` Step 5a already computes and confirms, not acceptance criteria, and classifying it `standard` is what loaded them as `autoTask` items that matched no QA-extraction keyword and reached Step 4b unmarked. `prd` and `proposal` share the fall-through and the map but deliberately do **not** redirect: neither command has an equivalent rollup to land in.
**Why `qa-required` is absent from the shared map (#2824).** `review-preamble.js` acts on every key of `issue-type.js`'s `REDIRECT_LABELS` with no honored set of its own, so adding the label there would send `review #N` — and a story that also carries the label — into `/qa`. An unassigned `qa-required` issue never reaches the redirect, because `gatherAllData` returns `NO_BRANCH` first; that error names `/qa`, which handles the assignment itself.
## Step 1c: why branch sync runs here and not per AC (#2635, #2687)
Between the last `/done` and this `/work`, local usually has nothing unpushed, so a fast-forward integrates another developer's push before any `Refs #N` commit is born on a stale tip.
> **Why here and not per AC (#2635):** nothing is pushed until `/done`, so a fetch per commit gains nothing and costs a network call each. The window this leaves open — commits accumulating while the remote moves — is closed by `/done` Step 2's rebase guard, the other half of the same change. Keyed to the moment, not the mechanism: it fires identically whether the ACs are worked inline or by a spawned Agent.
**Why `fetched: false` is reported for every stale-able status (#2687).** `up-to-date` is the case that matters most, since it is the one that otherwise reports nothing and so hides a stale all-clear behind silence. `no-upstream` is excluded because `fetchUpstream()` returns `false` whenever no upstream is configured, so a caveat there would report configuration as fetch failure.
## Step 2a: why an unknown verification mode resolves strict (#2556)
A project that declares nothing behaves exactly as it does today; the carve-out is reached only by an explicit, recognized declaration. Failing an unknown value into the carve-out instead would let a typo silently relax a gate while the config still looked deliberate.
## Step 3: the Review-State Gate (#2577, #2748, #2749, #2750)
**Why a decline is not recorded durably.** Unlike `/create-backlog`, this gate is evaluated on every `/work` invocation, so a persisted bypass mark would suppress it forever after a single decline.
**Why the gate runs before the Pre-Work Status Gate.** Accepting the offer means no work happens, so the issue should not have been moved to `in_progress` on its way back to the user.
> **Why `--nonstop` halts on `findings-pending` but only warns on `never-reviewed` (#2577):** halting on unresolved findings is consistent with `--nonstop`'s existing contract that any test/AC/QA/`gh pmu` failure halts immediately — working an issue whose criteria a reviewer has already flagged is the same class of problem. `never-reviewed`, by contrast, is the *normal* state of sub-issues `/create-backlog` has just materialized; halting on it would stop nearly every autonomous epic run on its first sub-issue. Batch mode shares the `--nonstop` rules except that `findings-pending` prompts rather than halting, because a human is present to answer.
>
> **Amended again by #2750, and the original objection does not reach a typed selection at all.** The rationale above argues from *freshly materialized epic sub-issues* — `never-reviewed` is their normal state because `/create-backlog` just created them in bulk, so halting there would stop nearly every autonomous run on its first child. A hand-typed `/work 44 47 68` is the opposite case: the user selected those numbers deliberately, one at a time, and nothing materialized them moments earlier. So the argument for warn-and-proceed is not weakened for selections — it simply never applied to them. Kept rather than deleted because it remains the reason the per-sub-issue behavior is correct where it still applies.
>
> **Amended by #2748, not overturned — the objection was correct and is now answered rather than ignored.** The reasoning above is entirely about *when* the question is asked. Warn-and-proceed was right for a gate firing **per sub-issue at its own turn**: halting there stops an autonomous run on its first freshly-materialized child, over a state that is normal for every one of them. Step 2b-ii asks **once, up front, about the whole tree**, and that changes what the answer costs — a single question before any work begins, naming every unreviewed member at once, is not the per-child interruption this paragraph rejects. So `never-reviewed` now stops and asks at Step 2b-ii for epics and for branch trackers under `--nonstop`, while this per-sub-issue gate keeps warn-and-proceed exactly as written for every other shape. Both statements are true simultaneously because they describe different moments; deleting this paragraph would lose the reason the per-sub-issue behavior is still correct where it still applies.
> **Why `indeterminate` fails open — a deliberate choice, not an oversight to be "corrected" (#2577):** an unreadable body, a contradictory `reviewed`+`pending` label pair, or a `gh` outage all yield `indeterminate`, and the gate proceeds. Blocking instead would let a GitHub outage stop all work; prompting would train users to dismiss the gate on issues it cannot actually classify. The classifier reports `indeterminate` explicitly rather than defaulting into a state, so the fail-open is visible in the verdict rather than buried in a guess.
## Step 3: the Pre-Work Status Gate (#2483)
> **Why keyed to the moment, not the actor (#2483):** this gate previously read "before spawning any Agent for implementation work". That wording made the check conditional on the *mechanism*, so the direct-work path — which rule 08 explicitly sanctions — bypassed it entirely, and sub-issues were worked without ever reaching `in_progress`. Keep the trigger phrased as a workflow moment; an actor-keyed rephrasing reintroduces the defect under a new name.
The gate covers two distinct failure modes: **compaction** between the Step 1 preamble and the start of work losing the status transition, and — for epics and branch trackers — the preamble having moved only the tracker, never the sub-issues. A tracker created by `gh pmu branch start` is already `in_progress`, so the preamble's move of it is a no-op that changes nothing about the sub-issues.
## Step 3: peer announcements, events 1 and 2 (#2662, #2674, #2699, #2702, #2705, #2790)
**Why the environment variable is read by the resolver, not here (#2705).** Precedence is `IDPF_X_SESSION > framework-config.json crossSessionMessaging > enabled by default`. Reading `process.env` in the rule would be a seventh copy of the rule, in the consumer most likely to be copied into the next command. A recognized off-value (`off`, `0`, `false`, case-insensitive after trimming) is all-or-nothing; **any other value leaves messaging enabled** and is reported as unrecognized, because a typo that silently mutes a session is undetectable by anyone — dispatch is already invisible from the sending side (#2674).
**Why the source is reported when it is `environment`.** A run that emits nothing because of a session-scoped variable, while `framework-config.json` says the groups are on, is otherwise indistinguishable from one where the announcement helper failed. Paraphrasing the resolver's `implications` entry as "messaging disabled" sends the reader to the wrong file.
**Why there is no per-invocation skip notice (#2702).** A disabled group is the user's own choice, so restating it on every `/work` is precisely the noise the setting exists to remove. Discoverability is placed where the setting lives instead — the startup `Peers:` row and `/x-session-config`'s opening display. This is the deliberate exception to *a gate that quietly does nothing is indistinguishable from one that passed*: here the silence **is** the requested behavior.
**Why the config is resolved once.** It is a project setting, and a second read inside one invocation is a second chance for the two to disagree — under `--nonstop` that would mean event 1 firing for one sub-issue and not the next, for no reason a reader could reconstruct.
**Why the payload is never hand-composed (#2790).** `buildAnnouncement` is still exported and still works, and calling it directly is exactly how the defect happened: a prose instruction to build a list is executed by a model, and the model composed one instead of deriving it. Event 1 carries no commits, but the ledger record it writes is what makes a *missing* event 1 attributable at Step 6a, and that record only exists if the script composed it. The event 2 commit set replaced a prose instruction to run `git log` by hand, which produced the observed defect: a `work-completed` naming `0a08fd7f` — never an object in that repository — while the real `e3ea5f02` for the same issue went unnamed. Two SHAs sharing no prefix is not a transcription slip; it is a list that was composed rather than derived.
**Why a failed send is recorded.** The observed run reported nothing on either side, which is indistinguishable from a send that never happened. A composition left at `pending` is surfaced by the Step 6a pairing audit, so forgetting the close-out degrades to a late report rather than to silence.
**Why `shouldSend` is not delivery (#2674).** It answers "is there anyone to send to" and nothing more. A send may still be held, declined, or left to expire by the receiving session, and none of that is observable at send time.
**Why event 1 is placed after both gates.** Emitting at Step 1 would announce work that a Step 1a CI-wait exit (1/2/5), a Step 1c `diverged` verdict, or the Step 3 Review-State Gate itself may still stop. A peer told that work began on an issue nobody touched is worse than silence, because it is actionable and wrong.
**Why event 2 fires per sub-issue (#2699).** Event 2's placement is stated as a workflow moment because `--nonstop` deletes the anchor the old placement used: it removes the STOP directive for every sub-issue but the last, so a placement expressed only relative to that STOP has no anchor for the other N−1, both readings conform, and a receiver cannot tell which a sender picked. Three reasons for the per-sub-issue reading, all pointing the same way:
- **Pairing — the load-bearing one.** Event 1 fires per sub-issue, so an end-of-run event 2 leaves every completed sub-issue carrying an unmatched event 1 for the remainder of the run, and silence stops distinguishing *not sent* from *not delivered*. That is the observed incident: a peer received event 1 for a completed sub-issue, received no event 2, and wrote into its user's summary that a message had been held, declined or expired. It had not been sent. This is the same "every opener has exactly one closer" property that makes `/done`'s events 3, 4 and 5 a single gated group rather than three toggles.
- **Attribution.** The payload carries that issue's `Refs #N` commit set. One message covering five sub-issues flattens per-issue attribution — exactly what `scope-drift-check.js`, `log-changed-files.js` and `nonstop-audit.js` key off.
- **Timeliness.** `--nonstop` runs are long and unattended. Deferring every completion to the end withdraws the advisory value at the moment it is worth most.
`buildAnnouncement` accepts many issues, and that capacity is what an end-of-run reading would have required; it is deliberately unused, which is why `issues: [$ISSUE]` is singular.
**Why the review-lifecycle events matter to `/work` (#2765).** Step 3's Review-State Gate reads the `reviewed`/`pending` labels and the `**Reviews:** N` marker — exactly the surfaces an in-flight `/review-issue` rewrites — so a peer's review announcements are what tell a session its classification is going stale. Rule 09 is their single definition; a guard test fails if an event name appears in more than one rule source.
## Step 3: the mid-AC commit checkpoint (#2557)
Naming the milestone is half the mechanism, not decoration. The delta decides **when** to ask; the answer supplies **what the commit message says**. A bare volume trigger would fix the uncommitted-work half of the failure and leave the bad-attribution half untouched. A hard gate mid-investigation would interrupt exactly the flow it exists to protect, which is why it offers rather than forces. It applies to standard single-issue `/work` because the reported incident was a standard run, which the Step 6a audit does not cover.
> **Why this threshold differs from Step 6a's commit-density audit, deliberately (#2557):** the two measure **different units** and are **not reconcilable to a single number**. This checkpoint measures **volume within one AC** — `changedFiles`/`insertions` since the last commit — and fires **live**, during work. `nonstop-audit.js` audit (1) measures **commits per AC** across a finished run (`Math.ceil(acCount / 3)`), and is post-hoc, warning-only, and scoped to epic/`--nonstop`. The post-hoc audit is left **unchanged**; this is additive. Attribution is why it matters: `scope-drift-check.js`, `log-changed-files.js` and `nonstop-audit.js` all key off `Refs #N` commit sets, so one misattributed commit degrades three separate gates.
## Step 3: host-process verification mode (#2556)
**Why the trigger is not "no automated tests exist."** A project that could run automated tests but has not written them stays on `automated-tests` and stays subject to the strict gate — keying on the absence of tests turns a narrow carve-out into a universal opt-out, which is the one outcome this must not become.
**Why it is distinct from the null-checklist fallback.** There `tddChecklist` is missing; here it **loads validly** and its RED gate is simply unsatisfiable, so the `== null` fallback never fires and nothing else catches it.
**Why "verified live" needs a named method and captured output.** Without them it is indistinguishable from not having verified at all, which is the failure this mode exists to prevent rather than to license. **Why disclosure is mandatory:** before the carve-out existed, a project verifying properly against a runtime log was indistinguishable from one skipping the gate, because neither said anything. The declaration authorizes the different evidence; the disclosure records that it was actually gathered.
> **Why the mode lives in `framework-config.json` and not in `tdd-checklist.json` (#2556):** the checklist sits closer to the gate it modifies, but it belongs to the **imported** `tdd-process` skill — its schema is `additionalProperties: false`, and `/fw-import-skills` replaces imported skills wholesale, so a field added there is reverted at the next import. Mirroring this into the skill is a cross-repo change against `idpf-praxis-skills`, not something this repository can deliver. The key follows `testCommand`'s precedent (#2595): declared by the project, no invented fallback, and an absence that is reported rather than papered over.
## Step 3: empty acceptance-criteria sections (#2614)
> **Why the distinction is worth reporting at all (#2614):** an empty AC list passes every downstream gate **vacuously**, not by succeeding. No per-AC subtasks are created, Step 4 has nothing to verify, Step 4b's force-move prohibition finds no unchecked boxes, and Step 6a's checkbox audit reports clean. An overcount announces itself; a vacuous pass is indistinguishable from a clean run unless something names it. `sectionFound` was added in #2600 and read by nobody until #2614 — the signal existed while the benefit did not.
Neither code blocks, because a proposal issue correctly has no acceptance-criteria section.
## Step 3b: why the doc judgment is recorded either way (#3176)
Every other Step 3–5 obligation leaves evidence a later check can read: ticked boxes, `### Files Changed`, sweep output, the `in_review` status. A "no doc" answer left none, so a skipped judgment looked the same as a negative one, and in one observed `--nonstop` run Step 3b was never evaluated for any of eight sub-issues with nothing reporting it.
## Step 4: out-of-phase ACs and the gate tokens (#2508, #2726)
**Why a gate token must name its resolving event (#2726).** Of the three live `→ GATE: review` ACs in this repo when #2726 was filed, one named a condition no gate phase describes (an external repository publishing a release) and two were satisfiable during implementation and not out of phase at all. The token had come to mean "I cannot tick this now" rather than a phase claim.
**Why shape is validated but the claim is not.** `nonstop-audit.js` pins `GATE_PHASES = ['review','release']` and matches the literal; `checkbox-scan.js` knows nothing of `GATE` or `QA` markers; `/done` performs no AC checkbox verification at all. Every one of those guards rejects an **unrecognized** token and none can detect a **recognized** token misapplied — which is the failure that actually occurred, twice out of three live instances. The reviewer-side check is `/review-issue`'s `ac-phase-feasible` criterion. A stricter regex still cannot read a claim.
**Why the authoring gate is the first line of defense.** `/create-prd`, `/create-backlog`, `/add-story`, `/bug` and `/enhancement` apply the `phaseFeasibility` prompt — all five **since #2726**; #2508 wired only `/add-story` and `/create-backlog` while the rule already named five, so for eighteen issues the `/work` fallback was the primary path.
**Why test-plan approvals left the force-move list (#2784).** Their gates are **resolved** by `/review-test-plan` Step 5a — computed, confirmed with the user, and checked off on both surfaces by declared text — not bypassed by a force-move. `/work` redirects such an issue at Step 1 and never reaches Step 4b for one, so an entry permitting a bypass there described a path that should not exist.
## Step 4e: why a registrar rather than a checklist (#2620)
> **Why a script rather than a longer checklist (#2620):** the `shared/lib` manifest key contains a slash, so it **cannot** be dot-accessed. A dot form reads `undefined` silently rather than erroring, and the idiomatic `|| []` guard turns that into a plausible-looking `false`. That hazard was already documented in rule 08 and was still paid by hand every time — most recently in #2600 for `lib/checkbox-scan.js`. Documentation cannot fix a transcription error it has already warned about; a tool can.
## Step 4c: two scopes, and the registrar exemption (#2788, #3261)
The Files Changed append happens *before* the scope-drift gate runs, so a single scope would let the run license its own protected edits — the gate's input derived from its own subject. The registrar exemption keys on co-occurrence because touching a shared helper is ordinary work, so keying on that alone would re-open the hole; an absent or malformed block exempts nothing, because absence must never widen a gate.
## Step 4f: the verification sweep (#2595, #2733, #3012, #3025, #3201, #3202)
**Why one run can stand for several suites (#3025).** Running a merged command once per suite would execute the same tests twice against the same tree, and a load-flaky test could pass under one id and fail under the other.
**Why `prepare` failure skips `full`, and why `runner not found` is separate (#3012).** A test run against an unbuilt tree reports a failure that is not the code's, which is worse than no result. For a missing runner the remedy is the host toolchain, not the tests, and the report says which binary so the reader is not sent to fix a suite that never ran. A rule that re-derived the verdict would give one outcome two definitions.
**Why unnamed skipped suites are a problem (#3026).** `/charter --testing` recommends `sweep: false` for e2e suites, so a skipped suite is routine rather than rare; unnamed, a suite the sweep deliberately left out reads exactly like one never declared.
**Why selection narrowing is safe (#3201).** This sweep is a check before review, not the merge gate. CI runs the full suite with coverage on every pull request to main, so a test a selector misses fails at the pull request instead of merging.
**Why `--nonstop` sweeps once at the end (#3202).** No human acts between sub-issues, so a per-sub-issue sweep buys only an earlier attribution of a cross-cutting failure, at the cost of the whole suite once per sub-issue.
> **Why the declaration widened and the rule did not (#2733):** `testCommand` could express one command, so this gate ran 1 of the 4 verification steps this repo's CI runs — and could not reach the 29 test files Jest is *configured* to ignore via `testPathIgnorePatterns`, which no flag change to a single command could have reached. The fix is more declaration, not more rule.
> **Why this rule names no runner, and must keep naming none (#2595, preserved by #2733):** the tempting simplification is to hardcode this repository's own linter invocation into this step. It is correct for Node and silently wrong for Go, Rust, .NET and Python, which is the original defect reintroduced one layer down. A rule naming *any* runner is wrong for some ecosystem, so this one **names none**: the project supplies every command, the framework supplies no default and no fallback runner. Declaration is the mechanism; detection and install-time seeding are deliberately separate questions (the latter belongs to Praxis Hub Manager).
> **Why the sweep degrades rather than halts:** an undeclared verification set is the normal state of every project until someone declares one, so halting would block `/work` everywhere on keys no installer writes yet. Fails open and says so — the same choice the Review-State Gate makes for `indeterminate` and Step 3 makes for an empty AC section.
## Step 6: autonomous processing and resume (#2751, #3270)
**Why resume never reads `gh pmu sub list` alone (#2751).** Its output carries only GitHub open/closed state (`[ ]`/`[x]`, or `state` under `--json`), never board status. An `in_review` issue is still `OPEN` and shows `[ ]`, so resuming on that signal re-works a sub-issue already finished. Deriving board status without the preamble costs one `gh pmu view $N --json=status --jq='.status'` per child.
