# GitHub Workflow Integration — Rationale
**Version:** v0.112.0
**Source:** Reference/GitHub-Workflow-Rationale.md
The reasoning behind decisions `Reference/GitHub-Workflow.md` (rule 02) directs without re-arguing (#3252). Nothing auto-loads this file; rule 02 names it. It ships with every other `Reference/` document and is never registered under `deploymentFiles.rules`.
## Pre-Work Status Gate (#2483)
The gate covers two distinct failure modes: compaction between the `/work` preamble and the start of work losing the status transition, and — for epics and branch trackers — the preamble having moved only the tracker, never the sub-issues. It was previously named for Agent spawning and triggered on it; keying it to the mechanism meant the direct-work path bypassed it entirely. The trigger is now the workflow moment — work beginning on an issue. `/work` Step 3 in `Reference/work-execution.md` states the same contract; the two must be changed together.
## Commit keywords
GitHub automatically closes issues when commits containing `Fixes/Closes/Resolves #XXX` are merged to the default branch. That bypasses the STOP checkpoint and closes issues without user approval.
## Issue-creating commands are not substitutable
`/bug`, `/enhancement` and `/proposal` are the mechanism for filing their issue types — not the preferred one of two options. **What a bypass loses:** the issue template; the acceptance-criteria feasibility gates, `verificationGate` and `phaseFeasibility`; prior-art handling; the priority default; and the reports-number-and-STOPs contract. None is visible on the created issue — it lands on the board correctly labeled, and nothing reports a problem. A consequence a reader can check is what makes a prohibition hold; "prefer slash commands" names none, which is why the earlier wording did not survive contact with a session looking for a license.
**Why several filings are not a fallback reason.** A `Skill` invocation transfers control and does not return, so at most one issue-creating command runs per turn. A batch of bugs or enhancements — `/code-review` Step 8's approved findings — goes through `.claude/scripts/shared/file-issue.js` (#3049), the creation path `/bug` and `/enhancement` themselves call: one invocation, same template, caller-supplied priority, and the judged gates it did not apply named per issue. A per-item `Skill` loop files one issue per turn. Outside a batch, more than one filing means more than one turn, never abandoning the command: name the filings still outstanding so the remainder has an owner.
**Three axes meet here, and satisfying one says nothing about the other two.** Which board is reached is settled by § QA-Issue Creation Ownership, including its `--target` exception. Which CLI form is used is `gh pmu` versus the bare `gh issue` creation form. Which command does the filing is the slash command versus a raw invocation. The same `gh pmu create` literal is correct for a standalone QA issue and wrong for a bug because the clauses answer different questions.
## The bare `gh issue` creation form (#2724, #2775, #3060 item 8)
The bare form files a GitHub issue that never reaches the project board, so it is invisible to `gh pmu sub list`, to epic closure, to `/done`'s sub-issue checks and to the `/work` Step 4b QA force-exception. The failure is silent and occasional, which is exactly why it survives: nobody notices until an epic will not close. Rule 05 used to restate this prohibition; since #3252 rule 02 owns it and rule 05 points here.
**The `--target` exception.** `gh pmu create -R <owner/name>` takes the *repository* from `-R` but the *project* from the local `.gh-pmu.json`, with no override flag, so it files the issue into the companion and adds it to **this** repo's board. Observed 2026-09-04 filing px-manager#1155: it landed on Project-Varia rather than the px-manager board. `file-companion-issue.js` creates the issue with the bare form and adds it to the companion's board explicitly, resolving field and option ids from that board; a name that does not resolve is reported unset, never guessed. The property the rule protects — that a filed issue reaches a board — still holds; what changes is *which* board. The `-F` / `--body-file` shell-safety rule applies to the bare form exactly as to `gh pmu`.
**`$QA_BODY_FILE` (#2991).** A fixed name is shared by every session filing QA issues in the working directory, so the body file is a creation path with a shelled-out suffix.
## QA closure contract
Moving a parent to `in_review` with `--force` past a `→ QA: #N` line is permitted only because the line names the sub-issue that still owns the check — the gate has moved, not disappeared. Closing the parent while its QA issue is open defeats it. `qa-required` is what makes the issue recognizable as a gate to every consumer that looks for one; an unlabeled QA issue is an ordinary issue, and nobody will treat it as blocking.
## Terms acceptance
The terms gate exists so users knowingly agree; the full terms text is in the error output of any `gh pmu` command that fails on missing or outdated acceptance. `gh pmu accept` without `--yes` needs interactive stdin, which Claude Code does not have.
