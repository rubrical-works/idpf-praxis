# Review Execution Rule — Rationale
**Version:** v0.111.0
**Source:** Reference/review-execution-rationale.md
Reasoning behind decisions rule 09 directs without re-arguing (#3009). Never auto-loaded; rule 03's On-Demand table names it. Ships as a `Reference/` document; never under `deploymentFiles.rules`.
## Why one rule serves both commands (#2737, #2746)
**Why one rule for both.** `/resolve-review` Step 4 invokes `Skill("review-issue", "#$ISSUE --force")`, so one issue's cycle previously injected `review-issue.md` twice. Hoisting both together is what makes the cycle pay for itself in under one issue.
**Both commands are MANAGED with zero `USER-EXTENSION` blocks (#2746).** `/review-issue` carried three points — `pre-review`, `criteria-customize`, `post-review` — all retired: never filled here, 0 of 28 recipes targeted them, and the declarative need is already served by `review-criteria.json`, `review-mode-criteria.json` and `review-extensions.json`, which the preamble reads. Removes the one command spanning two deployment mechanisms, so this rule matches rule 08's shape with no exception to document. The names live on in `extension-points.json` `deprecatedExtensionPoints`, beside `/work`'s four from #2368.
## Step 1: why `--prior-art` is no longer fatal at the preamble (#2752)
Previously absent from the argument loop, it fell through to the positional branch and was rejected as an issue number — `ok: false`, routed to **STOP**, halting the review before any criterion ran. Collecting unrecognized flag-shaped tokens into `unrecognizedFlags` is `02-github-workflow.md`'s pass-through convention.
## Step 1: why `--prior-art` must survive a redirect (#2725)
`/review-proposal` carries its own 2a-iv, so a dropped flag is a typed sweep request answered with silence — the discard `02-github-workflow.md` forbids. `/review-prd` and `/review-test-plan` receive it for uniformity and report it inapplicable.
## Step 1c: why openers and verdicts alternate (#2879); why suppression moved into the script (#2871)
A batch sending every opener first and every verdict after sent one per issue yet told peers reviews began that had not, leaving every opener unmatched until the batch ended — a dropped verdict indistinguishable from a queued one (#2781). Not observable from inside the repository, so not enforced. The `--force` suppression moved into `announce.js` because as a sentence it was skippable, as #2871 observed. No caller unwraps a peers envelope, so the #2678 mistake (module-level `peers` read where the CLI's `data.peers` was meant — "no peers" reported while two were reachable) has nowhere to happen.
## Step 2a-ii: why the file list is derived every review (#2520); parser history (#2523, #2813)
The old trigger tied the list to *repairing* a bad Proposed Solution, so a well-authored issue never got one — careful authoring guaranteed a later Step 4c halt.
So: **no blank line inside the block**, and **do not follow a bullet list with a table** — the table terminates the declaration rather than extending it. Load-bearing, not cosmetic: before #2813 any table below the declaration continued it and every backticked token in it became a declared path, and since #2788 `authoredPaths` is the only scope that can license an always-protected edit — so a row naming a protected path licensed the edit, **including a row whose prose forbade it**. The parser read the prohibition as permission.
**This paragraph previously stated the opposite** — that the section ended at the first blank line and that a table yielded empty declared scope. Both were falsified by #2523 and were still here when #2813 was filed; a reader following the old text would author a table declaration expecting it to be ignored.
**Payoff:** a declared path is exempt from the always-protected halt (`checkDrift`'s `isProtected && !inDeclared` guard), so an issue declaring what it touches clears Step 4c without a `Scope-Override`; since #2520 a declaration no longer forces blocking mode, files added during implementation warn as growth.
## Step 2a-iv: why `createdAt` comes from the envelope (#2539)
Before #2539 the preamble emitted no such field, so `decideSweep` returned `not-applicable` for every unmarked issue — a correct-looking skip. Exempting an unparseable date is the safe direction; the cost is that a missing one reads as a skip on the merits.
## Step 3: why the discoverability tip is never listed (#2812)
Three prose copies each listed 8 domains against a registry of 11, leaving the surplus three accepted if typed and advertised nowhere.
## Step 3b: the verdict-event vocabulary (#2722, #2781)
**Silence therefore has exactly one meaning: no review ran, or `groups.review` is off.** Before #2781 it also meant "the review found problems", which is what made it useless — a vocabulary where silence already means *dispatched but not delivered* (#2674) cannot carry a third sense.
A recommendation-keyed trigger reads as equivalent and is wrong the moment it is copied to a sibling command whose enum is wider — same gap, needing a stricter predicate rather than a copied trigger.
> **Why this does not overturn #2722, which declined a pending counterpart:** its reason was that *"adding one would assert a completeness the sender cannot have"* — correct about a **terminal** pending event, silent about a non-terminal one. #2716 had already separated the axes when it moved `armed` out of the terminal outcomes so a follow-up could come. **Do not "harmonize" the review events by adding `REVIEW_FINDINGS` to `TERMINAL_EVENTS`** — that re-asserts the completeness #2722 correctly refused, and a guard test fails on it.
**Mixed-version peers are unaffected, because no receiver parses an event name (#2781).** Announcements travel as plain prose through `SendMessage`; `KNOWN_EVENTS` is consulted only inside `buildAnnouncement`, in the **sending** session's own process against its own vocabulary. A peer on an older framework receives a readable sentence and never consults its own `EVENTS` set. The only consumer anywhere matching on an event *name* is `/overwatch`, and it enumerates the vocabulary in **two** places rather than reading `EVENTS`: `.claude/metadata/overwatch-signals.json` `observation.events`, and the **Events consumed** list in its own command spec, which `overwatch.test.js` asserts against `Object.values(EVENTS)`. Both are part of adding any event; the spec list is the one that gets missed. An older monitor still receives the message and simply does not classify it.
**Terminal, and the text says so** — alone among the four review events nothing follows `review-passed`, so a peer can stop waiting; a `terminal` flag no reader of the message ever sees is not a closer.
## Step 3a: the `labels` shape (#2682)
`isEligibleForInterdependence` reads both shapes — `['story']` hand-built, or `[{name:'story'}]` as `context.issue.labels` arrives — and an input it cannot read warns rather than returning a bare `false`. Flattening is unnecessary, and a flattened array that lost a name would read as "not eligible" with no warning.
## Epic expansion caps: how they were sized (#2869, #2872, #2958)
The caps and their measured basis stay in `review-execution-conditional.md` beside the bodies they bound. History: review cap six (#2869), resolve cap three (#2872), both for a 200k window (six children ≈ 75k; six pending ≈ 185k, three ≈ 160k). #2958 raised both to 20 for a 1M base from the eleven-child epic #2843 (`Construction/Design-Decisions/2026-09-10-epic-review-expansion.md`): ≈ 12k per child reviewed, ≈ 8k more resolved — 20 reviewed ≈ 240k, 20 resolved plus re-review ≈ 400k, estimated not re-measured. Safe because recoverable: per-member tasks batched after the epic's preamble. #2963 made both a project setting (`framework-config.json` `reviewExpansion`, via `resolveReviewExpansion`), default still 20 — a resize is a config edit, not a hand-edit of every literal.
## `/resolve-review` Step 3a: why suggestions are reported (#2717)
**Why (#2717):** `review-finalize.js` accepted `suggestions` and discarded it, so a suggestion-only defect passed the whole resolve cycle untouched and emerged under a clean `Ready for work`. Rendering it fixed only the visible half; without this step the envelope carries the key and nothing reads it — the silent drop moved one layer along.
## `/resolve-review` Step 4: why `--prior-art` is only forwarded (#2725)
Re-implementing the sweep decision would give one workflow two answers. Under `reviewSweep: off` the refusal surfaces from the nested re-review, which reports the message and continues; nothing is refused here and the cycle does not halt.
## Step 3a: why the epic is excluded from interdependence (#2869)
`typeFilter.excluded` covers the epic type and the step requires every member eligible, so the whole expanded set returns all-eligible false and the analysis is silently skipped — indistinguishable from one that found nothing. The exclusion is right: a container's scope necessarily overlaps its children's, and reporting that is noise.
## `/resolve-review` Step 1b: why the feasibility gate exists here (#2726)
Until #2726 this was the only AC-authoring path with no feasibility gate; neither Step 2 nor Step 3 asked the two questions every other authoring command asks.
## `/resolve-review` Post-Complete Cleanup: why both task sets are cleared
Without the sweep the next command inherits stale tasks plus the re-review's preamble/evaluate/finalize/closing tasks, and compaction recovery misreads them as incomplete work. The review-issue Step 4 prune precedes the notification for the same reason: a prune placed after what makes a run feel finished never runs.
## `/resolve-review` Step 3a: why suggestions are never classified (#2717)
`classifyFindings` sorts on `f.status`; its `warn, skip, or unknown` fallback would drop a suggestion into `needsUserInput`, asserting a severity the reviewer never expressed.
