### Step 1b: Epic Complexity Assessment
Trigger: `context.type=="epic"` and `--nonstop`. `node .claude/scripts/shared/epic-complexity.js $ISSUE`. `classification=="functional"` → `strictTDD=true`. Signals: `.claude/metadata/epic-complexity-signals.json`.
### Step 2b: Prime Sub-Issue Task List (epic/branch)
Trigger: `context.type in {epic, branch}`. After Phase 2, take the active set from the **envelope Step 1 already parsed** — no CLI call. `context.subIssues` is the full child list (active plus skipped, body/label-enriched per #2622), `context.skipped` is `[{number, status}]` (plus `reason: 'qa-required'` on a label skip, below), so active = `subIssues` minus `skipped`: a complete partition at zero extra round trips. For each remaining, in `context.resumeOrder` order (#3270), `TaskCreate` subject `Sub-issue #N: $TITLE` with description `Per-sub-issue parent — owns AC subtasks and this sub-issue's turn of Steps 3, 3b, 4, 4a, 4b, 4d, 4e, 4c, 4f (default mode), 4g, 5.` Parents make compaction-recovery resume self-describing: `TaskList` alone shows active sub-issue.
**A `qa-required` sub-issue is skipped with a pointer, never redirected mid-loop (#2824).** Signal: `context.subIssues[].labels`, fetched by the same status query; `checkSubIssueStatuses` places such a child in `context.skipped` with reason `qa-required` — `{ number, status, reason: 'qa-required' }` — whatever its board status, so the active set excludes it and no parent task is created. Report each at its turn as `Sub-issue #N is qa-required → run /qa #N` and count it in the final `Nonstop Processing Complete` summary. A mid-loop `Skill("qa", …)` redirect was rejected: Skill *transfers control*, `/qa` ends at its own STOP, and nothing returns to the sub-issue loop — remaining sub-issues are silently never processed and the summary never prints. QA sub-issues are gates on the *parent's* closure, not work in sequence with siblings, so the loop loses nothing. The `/qa` redirect is single-issue only. `test-plan` sub-issues share the latent mid-loop gap — #2784's surface, not claimed here; the skip is written to carry a second label.
**Do not re-query — and do not "repair" the old call either (#2751).** This step previously instructed `gh pmu sub list $ISSUE --json=number,title,status` then an `in_review`/`done` filter. Neither half worked, and the second is why re-querying stays wrong even corrected:
| Half | What actually happens |
|---|---|
| the call | **Errors.** `--json` is **boolean** on this subcommand and takes no value: `strconv.ParseBool: parsing "number,title,status": invalid syntax` |
| the filter | Even in the working form the output carries **no board status**. Children carry `number, title, state, url, repository`; `state` is GitHub `OPEN`/`CLOSED`, never `in_review`/`done`. An issue can be `in_review` while still `OPEN`, so the filter is **underivable** from this output |

Working form is the bare flag `gh pmu sub list $ISSUE --json`, returning `{issue, children, summary}` — an object with a nested `children` array, not the flat array "for each remaining" implied. Board status needs one `gh pmu view $N --json=status --jq='.status'` per child.
`work-preamble.js` already does both in exactly those forms — `loadSubIssues()` calls the bare form and maps `result.data.children`; `checkSubIssueStatuses()` runs the per-child view and returns `{skipped, active}`. The run has already paid for this fact; re-deriving it here creates a **second** source of truth, and the second source is the one that drifts.
### Step 2b-ii: Tree-Wide Review Gate (epic — #2748; branch tracker + `--nonstop` — #2749)
Trigger: `context.type == "epic"` (#2748), `context.type == "branch"` with `--nonstop` (#2749), or a **non-epic selection of two or more issues** (#2750) — `/work 44 47 68`, `/work --status ready`. The same condition as rule 08 Step 1d: a single-issue selection (`/work 44`) is the degenerate case of the selection gate and runs it through Step 3's resident Review-State Gate, which classifies the one member the same way, so it never needs this file (#3248). A branch tracker worked *without* `--nonstop` skips this step and is gated per sub-issue by Step 3's Review-State Gate exactly as before.
**The selection gate in full (#2750).** A selection typed on one command line is classified **in full** before the first acceptance criterion of the first member is worked, and raises **one** question over the whole selection. This is an **addition**: the per-issue actions in `.claude/metadata/review-state-gate-actions.json` are unchanged, and its batch column still describes what the per-sub-issue gate does when it is reached.
- **N=1 is the degenerate case of the same path, not a second branch.** Its observable behavior is unchanged: `never-reviewed` STOPs and offers `/review-issue`, `findings-pending` STOPs and offers `/resolve-review`.
- **At N ≥ 2 a third option is offered: proceed with the clean members only**, and the run reports which issues were dropped and why. **At N = 1 it is not offered** — proceeding with the clean members of a one-issue selection proceeds with nothing, which is the decline path wearing a third label. The same suppression applies at any N where every member is flagged.
- **Dropping is natural here and nowhere else.** Removing one hand-typed issue from a list is an ordinary answer; removing a sub-issue from an epic or a branch tracker is not, which is why neither sibling gate offers it.
- **`--status <status>` selections are covered, deliberately, despite the cost.** Classification is one `gh issue view` per member, so an unbounded `--status backlog` pays that per member before any work starts. Covering it anyway is the choice: a `--status` selection is precisely the case where the user has *not* inspected the members individually, so it is where an unreviewed member is most likely and least expected. A size threshold was considered and rejected — it would make the gate silently stop applying at the selection sizes where it matters most.
- **A selection bypass is deliberately not recorded anywhere.** A selection has no container issue to write into; writing into each member's body would mark issues rather than the decision, and would leave a note on issues whose only involvement was being typed on the same line. The decision is session-scoped and not repeated within the invocation, including after compaction recovery.
**Which of the two review gates runs first, and what each owns (#2749).** On a branch tracker under `--nonstop` there are two, and they are not alternatives:
| | Runs | Scope | Owns |
|---|---|---|---|
| **Step 2b-ii — Tree-Wide Review Gate** | once, before the first sub-issue is worked | the whole processable set | the *unattended-run* decision: may this run proceed at all, given what is unreviewed anywhere in it |
| **Step 3 — Review-State Gate** | per sub-issue, at that sub-issue's turn | one issue | the *per-issue* decision, and the compaction-recovery safeguard for a member Step 2b-ii never saw |
**Step 2b-ii runs first and is strictly broader**, so a member it has already decided is not re-prompted at Step 3 — one decision per issue per invocation. It does **not** replace that gate: a sub-issue added to the tracker after Step 2b-ii ran, or a run resumed after compaction into the middle of the set, reaches Step 3 without having been classified up front, and Step 3 is what catches it.
**This moves *when* the gate fires without weakening *what* fires it (#2749).** The trigger is still a workflow moment — it has moved to an earlier one — and the direct-work path cannot bypass it any more than before, because Step 2b-ii runs before the first sub-issue regardless of how that sub-issue is later implemented.
**Three enumerations, one decision — what "one helper, not three" means in practice (#2748, #2750).**
| Gate | Enumerates | Tracker in scope? | Drop option? |
|---|---|---|---|
| Epic (#2748) | the epic **plus** every child from `gh pmu sub list` | **yes** — an epic is reviewed | no |
| Branch tracker + `--nonstop` (#2749) | the processable set of children | **no** — nothing reviews a branch tracker | no |
| Selection, 1..N (#2750) | argv, or the `--status` query result | n/a — a selection has no tracker | **yes, at N ≥ 2** |

All three resolve states with `review-state.js` and hand an already-resolved list to `branch-review-gate.js`. The differences are carried by **what the caller declares about its own input** — `isTracker` per member, `setShape` for the set — and by set size, never by an issue-type test inside the helper.
**The `Drop option?` column was unenforced from #2750 until #2780; both `no` cells were right.** `e0311002` added `proceed-with-clean` and in the same commit wrote three statements withholding it from the tree gates: both cells above and the rule-08 line *"Dropping is natural here and nowhere else."* The code gated on set size alone, so it offered the option to epics and branch trackers, and no test exercised a tracker-shaped set. Recorded intent was unanimous and the code was the lone outlier, so **#2780 corrected the code**.
**The epic row resolves the same way, for a stronger reason.** Unlike a branch tracker the epic *itself* is a classified member, so a drop could remove it from the gate while Step 6a still evaluates its ACs and moves it to `in_review`. One rule produces both rows: **only a hand-typed selection may drop.**
**#2749 did not withhold the option deliberately — it could not have.** The helper it created (`ec42f72b`) offered `review-issue` and `resolve-review` only; `proceed-with-clean` did not exist until #2750. Disproved, not merely unsupported.
Classify **every issue the run will process** before the first sub-issue is worked; raise **one** combined question over the whole set.
**Scope is the processable set**, not the tracker's children: members already `in_review`/`done` removed, preamble `skipped[]` honored, matching what Step 6a iterates. An unreviewed member the run never reaches is not a reason to stop.
**Whether the tracker itself is classified differs by type, and the reason is not symmetry:**
| Type | Tracker classified? | Why |
|---|---|---|
| **Epic** (#2748) | **Yes** | An epic *is* reviewed — own ACs, own `reviewed`/`pending` label, can carry its own findings. Excluding it lets an epic with unresolved findings drive a run of its own children. |
| **Branch tracker** (#2749) | **No** | Nothing reviews a branch tracker: no ACs, never reaches `in_review`. Classifying it returns `never-reviewed` every run and fires the gate on every invocation, training the user to dismiss it. |

The helper takes this as **data, not an issue-type test**: pass the branch tracker with `isTracker: true` and it is dropped; pass the epic without the flag and it is classified like any member. A type branch inside the helper would make it three helpers wearing one name.
**Enumeration is what the two gates do differently; the decision after it is identical.** The epic gate enumerates the epic plus every child; the branch gate the processable set above. Both hand an already-resolved list to the same aggregator — the whole content of "one helper, not three" (#2748).
**The chain is a script, not a procedure (#2826).** Enumeration, per-child board status, per-member classification and the aggregation call live in `.claude/scripts/shared/tree-review-gate.js`, a **runner** around `lib/branch-review-gate.js` — no decision added, the I/O around one. Run it and act on its envelope; do not re-describe or re-derive those four steps inline:
```bash
node .claude/scripts/shared/tree-review-gate.js --issue $ISSUE [--tracker] [--skipped '<context.skipped as JSON>']
```
`--tracker` declares a branch-tracker root `isTracker: true`; an epic run omits it and the epic is classified like any member — the **Tracker classified?** table above as caller data, never a label test in the script. `--skipped` is `context.skipped` verbatim, so the set matches what Step 6a iterates. `setShape` is `'tree'` for both, withholding the drop (#2780).
Read `data`: `gate`, `options`, `neverReviewed`, `findingsPending`, `indeterminate`, `processable`, `members` (`number`, `title`, `state`, `boardStatus`, `isTracker`). `data.gate: false` → proceed silently. `data.gate: true` → **one** `AskUserQuestion` naming `neverReviewed` and `findingsPending`, offering `/review-issue` when `options` has `review-issue` and `/resolve-review` when it has `resolve-review`, both in one question when both are. **Accepting means work does not begin:** report the command and **STOP**, issues left as found. Declining proceeds with the whole run; no re-ask within the invocation, including after compaction recovery. Relay `warnings` verbatim — each names the member whose read failed.
**Two failure modes, two answers, both the script's.** `ok: false` with `ENUMERATION_FAILED`: **STOP and report** — a gate computing its scope from a call that errors classifies nothing and passes vacuously, the #2751 defect exactly. A failed read of one *member* is fail-open: `indeterminate` (classifier) or null `boardStatus` and still processable (board), with a warning naming it. `indeterminate` never prompts (#2577) — blocking would let a `gh` outage stop an autonomous run. Returned in its own bucket so the pass is visible, not indistinguishable from a clean classification.
**The selection gate (#2750) rides the same script via `--issues`.** `node .claude/scripts/shared/tree-review-gate.js --issues "44,47,68"` classifies argv members with no enumeration and no root, declares `setShape: 'selection'`, so offers `proceed-with-clean` at N ≥ 2 with `data.clean` naming who proceeds; a `--status` selection passes its query result the same way. `--record-bypass` on a selection writes nothing (`reason: selection`) — no body to record into, the #2750 rule that a selection bypass is never recorded.
**Where a bypass is recorded differs by type — the sharper of the two asymmetries:**
| Type | On decline | Why |
|---|---|---|
| **Epic** (#2748) | **Run `tree-review-gate.js --issue $ISSUE --record-bypass`** — writes a dated note naming the flagged members into the epic body (idempotent: a second decline reports `written: false, reason: already-recorded`), then continue | An epic is a durable artifact a human returns to. A bypass is a decision about its readiness, and the body is where its other decisions already live. |
| **Branch tracker** (#2749) | **Write nothing.** `--record-bypass --tracker` is a no-op that says so (`reason: branch-tracker`). Continue | The body is machine-parsed for `**Processing Order:**` (#2622), so a free-text marker risks a parser with no schema for it. A branch tracker is transient — destroyed with its branch — so there is no later reader. |

**Neither recorded bypass suppresses the gate on a later run (#2748 AC8).** The epic's note records what was decided, not a flag the gate reads — `review-state.js` classifies from the `reviewed`/`pending` labels and `**Reviews:** N` only, so body prose cannot reach the verdict; `tests/scripts/shared/tree-review-gate.test.js` case (c) pins that mechanism by name. A suppressing bypass would silence the gate long after the state that justified it changed — a sub-issue added later, or findings raised after the decline, would never surface. Re-asking costs one question; not asking costs an unattended run over issues nobody looked at. Within one invocation the decision is not repeated, for either type.
> **Why up front (#2749):** the per-sub-issue gate discovers a tracker's fourth child carrying unresolved findings only after three have been implemented, committed and moved to `in_review` — where acting costs most. `--nonstop` removes the per-sub-issue STOP where a human would notice, so this is the one moment every option is still cheap.
### Step 2c: Proposed Work Order (`--nonstop` epic/branch — #2622)
Trigger: `context.proposedOrder` present. The preamble sets it only for `context.type in {epic, branch}` under `--nonstop`; absent in every other mode, so this step does not fire.
**Report before the first sub-issue is worked — three inputs, one report (#3128):**
| Input | Source | Status |
|---|---|---|
| **Graph order** | `context.processingOrder` vs `context.declaredOrder`, edges from `context.dependencyGraph` | **Applied** — `**Depends on:**` is explicit, so the run already works in this order; report where it differs from declared and name each edge that moved a member |
| **Heuristic suggestion** | `context.proposedOrder`, suggested edges in `context.orderRationale`, from `review-interdependence.js` | **Proposed** — never applied without acceptance |
| **Concurrency groups** | `context.concurrencyPlan` (`--concurrent` only) — groups by layer, each at most `--agents N` (cap on agents of any kind, default 3), then the tail with causes; whether `--no-review` will skip the gate's Tier 3 | **Derived** from the graph order; a zero-group plan falls back to sequential |
```
Work order for #$ISSUE:
  declared: #901 → #902 → #903
  graph:    #902 → #901 → #903   (#901 depends on #902)
  proposed: #902 → #903 → #901
    #903 creates declared scope src/order-helper.js that #901 also declares — provider should precede consumer
  groups:   [#902, #903] → [#901]; tail: none
```
**A proposal can never place a member before what it depends on** — the preamble re-sorts the heuristic topologically, so it only breaks ties the graph leaves open. The scope heuristic once proposed a story ahead of the one its own `**Depends on:**` named, reading "created in #N" as the story creating the file; a declared edge outranks inference from prose.
`context.orderDiffers==false` → report the proposal matches the order in effect, continue; nothing to decide.
**Ask once, then persist — only on acceptance.** Orders differ → offer **one** `AskUserQuestion`: accept proposed, or keep the order in effect. On acceptance write it to the tracker body via `gh pmu view $ISSUE --body-stdout` → `applyProcessingOrder(body, acceptedOrder)` → `gh pmu edit $ISSUE -F` → `rm`. On decline **nothing is written**; the run proceeds in `context.processingOrder` — the graph order, which a decline does not undo: its dependencies are declared, not proposed. The preamble never writes — `applyProcessingOrder` returns a new body and the caller persists it, which is what keeps the decision reviewable.
> **Why propose rather than apply (#2622):** the derivation is deterministic but demonstrably incomplete — measured over #2614–#2620 it surfaced one of two real declared-scope collisions and reported 21 boilerplate `sharedCriteria` matches. `--nonstop` removes the per-sub-issue STOP where a human would otherwise catch a wrong order, so a silent reorder would replace a knowably-wrong order with an unaccountably-wrong one, unattended. Surfacing costs one question; getting it silently wrong costs a sub-issue implemented against a provider that does not exist yet.
> **Why persistence reuses `**Processing Order:**`:** an accepted order must survive compaction, and that format is already parsed by `parseProcessingOrder` (#2544). The next run — this one resumed, or a later one — reads it through the mechanism that already exists, with no new state store to keep in sync.
### Step 3: `--concurrent` Test Scope and the Merge-Back Review Gate (#3117)
**Trigger:** `--concurrent` on an epic or branch tracker (Step 1d loads this file for those shapes).
**Under `--concurrent`, the `--agents` cap is also the unit-test concurrency cap (#3132).** Each member of a group runs its scoped suites inside its own worktree, so at most `--agents` test runs execute at once — and only suites a member may run there: `scopedInvocations({inWorktree: true})` returns the `parallel` suites and defers the `exclusive` ones (`e2e` by role default, or declared). The parent runs the deferred set through `deferredInvocations()` once per group, serially, on the tracker branch after merge-back, worktree teardown **and reconciliation** (#3272 — the deferred skills run first too, so these suites test the reconciled tree), scoped to the union of the group's changed files, regenerated paths included — never inside a worktree, never skipped. Neither that run nor Step 4f starts while a worktree of the group exists; `leftoverWorktrees()` names any `.tmp-wt-*` still under the root and the run continues.
**Merge-Back Review Gate outcomes (#3130, #3141).** Before a member's branch merges back, `merge-back-gate.js` runs three tiers: Tier 1 (mechanical — `Refs #N` on every commit, nothing uncommitted, scope drift, the member's parallel suites in its worktree), Tier 2 (the parent's own file-by-file read; the direct-work exemption never applies) and Tier 3 (an independent `diff-review` reviewer, never handed the implementer's summary). `--no-review` skips Tier 3 and an absent skill degrades to Tiers 1–2 — both reported, never silent. **The reviewer writes its own review (#3204)** to `.tmp-gate-<N>-tier3.json`, the one file it may write; the parent never saves or re-words its reply. The parent runs `tree-snapshot --clear .tmp-gate-<N>-tier3.json` before the spawn, which removes any earlier cycle's review, and `outcome --tree-before` fails Tier 3 as `tier-3-missing` when the file is absent, as `tier-3-stale-output` when the snapshot already listed it, or as `tier-3-wrote-outside-contract`, naming the paths, when anything outside this member's own review and snapshot and its running-group siblings' own gate files changed (#3220). **Scoped to the run (#3263):** when every running member's Tier 1 document names its declared scope, only a change inside those `runPaths` fails; a change outside them is listed as `external` (another session's) and reported, never failed — with any scope unreadable the check stays strict. **The merge comment needs no file (#3276):** `outcome --post-comment` posts `comment.body` through `gh issue comment --body-file -` on stdin, writes no root file, and returns `posted` (issue, comment id, url) or `postError` (exit 1). The snapshot check is the enforcement: the Agent tool has no per-spawn write restriction. **The Tier 1 document is verified the same way (#3225):** `tier1 --out .tmp-gate-<N>-tier1.json` writes it and reports the sha256 of the bytes it wrote, and `outcome` requires `--tier1-sha`; it too sits in the reviewer-writable root, so a file changed since halts as `tier-1-document-changed`, naming the file, and the member is never merged. **Pass or warn merges** the member and posts the findings as a structured comment on the sub-issue. **A fail buys exactly one fix cycle:** `decideOutcome` sends the findings to the same implementer by `SendMessage` with its worktree intact, every tier re-runs once, and **a second fail halts** under the `--nonstop` contract with files and lines, the worktree kept, the member never merged. **A reviewer-process failure is a re-review, not a fix cycle (#3222):** with Tier 1 passing, a Tier 3 `tier-3-missing`, `tier-3-wrote-outside-contract`, `tier-3-stale-output` or `tier-3-snapshot-changed` yields `re-review` — the parent re-snapshots, re-spawns the reviewer in the same slot and re-runs `outcome --review-retries 1`; the implementer's fix cycle is not spent on it, and a second such failure halts attributed to the reviewer. **A re-review never re-baselines over the stray writes (#3226):** after `tier-3-wrote-outside-contract` the `re-review` decision carries the named paths as `outsideContract`, and the parent reports and clears them before re-snapshotting — removing or restoring what this run wrote, and waiting for another session to settle a path it is editing, never deleting or reverting that session's work — so the paths cannot become part of the new baseline. Compaction mid-cycle: the parent re-reads the worktree branch and the resumed re-run of all tiers **is** the one cycle (`resumeFixCycle`). After the group's merge-back and reconciliation, Tiers 1–2 run once more in the parent over the members' diffs ∪ the runner's regenerated paths (`postMergeSet`) before the group is reported; a fail there halts on the same terms. **Reconciliation's outputs have a commit rule (#3272):** after the deferred skills, `regenerateAfterSkills` re-runs every generator that reads their outputs (the extension registry, after `fw-minimize-files` rewrites `.claude/commands/**`), and every path the reconcile, deferred-skills and that pass rewrote is committed once as `Refs #<root>` — the epic, or the branch tracker's own issue — then passed to `group-tier1` as `--regenerated` with `--epic <root>`. **Two group members changing the same file outside their declared scope halt merge-back before any merge** (`undeclared-overlap`, every member named), and `group-tier1` repeats the check over members' own commits; one member's out-of-scope path stays advisory (#2520) and is listed in its merge comment.
### Step 4f: Cadence under `--nonstop` (epic or branch tracker — #3202)
**Trigger:** `--nonstop` on an epic or branch tracker.
Each sub-issue's boundary is covered by its scoped tests (Step 3) and it moves to `in_review` without a full sweep; **one** full sweep — every run `sweepInvocations()` returns, reported per suite as rule 08 Step 4f directs — runs after the last sub-issue, before Step 6a, over the union of every processed sub-issue's changed files. Under `--concurrent` the per-group sweep gives way the same way: `buildRun()` emits a single run-level `4f` step after the last member. The shared Step 4f task is marked `completed` after that sweep. **On a failure, halt under the `--nonstop` contract and attribute it:** name each failing suite and test and, from the changed-file union, the sub-issues whose changed files those tests cover — a test file the sub-issue changed, or a source file it changed that the test exercises; when neither holds say `unattributed`, never guess. Processed sub-issues stay `in_review` — none is moved back — and the Step 6a summary reports the sweep failure as **blocking**: commit the fix under the attributed sub-issue's `Refs #N` and re-run the sweep. **A `--nonstop` halt before that sweep** — a failed worktree creation, a residual merge conflict, a second gate fail, any halt after at least one sub-issue reached `in_review` — leaves those sub-issues unswept: the halt report names them (`Not swept`, from `haltReport`'s `unswept` list and `merge-back --unswept`), and they must be swept before `/done`, because a resumed run skips `in_review` members. **Default mode is unchanged:** a per-sub-issue STOP keeps its per-sub-issue sweep.
### Step 4g: Independent Review (#3457)

**Trigger:** every issue, after Step 4f and before Step 5 — the resident directive in rule 08 runs `review-plan`; this is what to do with its result. Under `--concurrent`, a group member's review **is** the Merge-Back Review Gate's Tier 3 (§ Step 3), so Step 4g runs only for the sequential tail and for a lone member worked inline.

**Plan.** `node .claude/scripts/shared/lib/merge-back-gate.js review-plan --issue $ISSUE`, adding `--nonstop` and `--no-review` when the run has them. It resolves `workReview` through `framework-config.js` `resolveWorkReview()` — `always` when absent, `nonstop-only`, or `off` — and the issue's own `Refs #$ISSUE` commits since the branch's merge-base, and returns `review`, one of two things:
- **A reported skip** (`skipped: true`, `reason` one of `no-review`, `work-review-off`, `work-review-nonstop-only`, `no-commits`, `skill-absent`): report its `message` and continue to Step 5. A skip is never a pass, and never silent.
- **The Tier 3 reviewer request** the Merge-Back Review Gate uses: the issue's commit range and its own commits (another issue's commits can sit inside the range), its ACs, its `Files to modify:` and the charter — never the implementer's summary.

**Review.** `node .claude/scripts/shared/lib/merge-back-gate.js tree-snapshot --out .tmp-gate-$ISSUE-tree-before.txt --clear .tmp-gate-$ISSUE-tier3.json`, then spawn **one** read-only Agent with `review.request.prompt` verbatim — the brief carries the code and the ACs, nothing you summarize. It writes `.tmp-gate-$ISSUE-tier3.json` and nothing else. Then `node .claude/scripts/shared/lib/merge-back-gate.js review-outcome --issue $ISSUE --tier3 .tmp-gate-$ISSUE-tier3.json --tree-before .tmp-gate-$ISSUE-tree-before.txt --tree-before-sha <sha256 tree-snapshot reported> --post-comment`, adding `--fix-cycles 1` or `--review-retries 1` on a re-run. **The tree check is scoped to the issue's declared scope:** another session's write outside it during the review is reported as `external`, never failed; a write inside it fails the review as `tier-3-wrote-outside-contract`.

**Act on `action`:**
| `action` | Do |
|---|---|
| `proceed` | `pass` or `warn`: the `## Work Review` comment is posted (`posted`; report a `postError`). Continue to Step 5 |
| `fix` | The one fix cycle: fix each finding in a `Refs #$ISSUE` commit, re-run Steps 4c and 4f (under `--nonstop`, the scoped tests), re-run `review-plan` — the first plan's range ends before the fix commits — then re-snapshot, re-spawn with the new plan's prompt and re-run `review-outcome --fix-cycles 1` |
| `re-review` | A reviewer-process failure, not a finding: report and clear any `outsideContract` paths this run wrote, re-snapshot, re-spawn and re-run with `--review-retries 1` — no re-plan, since no commit was added. The fix cycle is not spent |
| `halt` | Report `report` and STOP before Step 5; the issue stays `in_progress`. Under `--nonstop` this is a halt under the `--nonstop` contract |

After `proceed`, remove the scratch with `node .claude/scripts/shared/lib/merge-back-gate.js clear-member --issue $ISSUE`.

**Cadence under `--nonstop`:** once per sub-issue, before that sub-issue's Step 5 — each range stays inside the reviewer's read budget, and a finding is attributed to the sub-issue that made it. The end-of-run sweep (§ Step 4f) does not wait for it, and it does not wait for the sweep.

**Compaction:** `tree-snapshot --clear` removes a review file from before compaction; re-run the review. A `Refs #$ISSUE` fix commit already made after a `fix` decision means the cycle is spent — re-run with `--fix-cycles 1`.

### Step 6: `--nonstop` and `--concurrent` Processing
**Trigger:** `--nonstop` or `--concurrent` on an epic or branch tracker.
**`--nonstop` mode:** same cycle as default mode, **no STOP** between sub-issues. Report `"Sub-issue #N: $TITLE → In Review (M/T processed)"`, continue. Ignored for standard issues. Step 4f runs once at the end of the run, not per sub-issue (§ Step 4f above). One commit/AC (`Refs #N`); commits local (push deferred to `/done`). Test/AC/QA/`gh pmu` failure halts immediately — report which sub-issue, count completed, resume instructions. A `findings-pending` verdict from the Step 3 Review-State Gate halts on the same terms (#2577). **Post-compaction:** re-read rule; `TaskList` — the `in_progress` sub-issue parent task (per Behavior Rule 7) is the primary resume signal. If no parent is `in_progress`, fall back to re-running the Step 1 preamble and resuming from the first member of `context.resumeOrder` — the dependency order, `context.processingOrder` minus `context.skipped` (#3270) — **not** to `gh pmu sub list $ISSUE` alone, which carries no board status (#2751): an `in_review` issue is still `OPEN`, so resuming on that signal re-works a sub-issue already finished. Final: `Nonstop Processing Complete` (processed/skipped/failed).
**A sequential halt is recorded on the tracker (#3270).** When a `--nonstop` run halts after any sub-issue reached `in_review` and before the end-of-run Step 4f, post a tracker comment carrying `buildUnsweptMarker(<those members>)` (`<!-- unswept: #a, #b -->`, `work-preamble.js`). A resumed `--nonstop` run returns it as `context.unswept`: the end-of-run Step 4f covers those members' changed files with its own, and once it passes, post `buildUnsweptMarker([])` to clear it.
**`--concurrent` mode (#3117):** on an epic or branch tracker, file-disjoint members whose `**Depends on:**` edges are met run at once in framework-owned worktrees, in groups of at most `--agents N` (default 3 — the cap on agents of any kind at once, reviewers and fix cycles included, and on unit-test concurrency); everything else falls to a sequential tail worked as standard `/work`. The parent owns every gate, event, merge-back and status move; each member agent owns Step 3 in its worktree. Before merge-back the Merge-Back Review Gate runs (§ Step 3 above); `--no-review` skips its Tier 3, reported. **One STOP per group**, after merge-back with every member `in_review`; the tail STOPs per member. **Fallback:** a plan with **zero groups** runs exactly as sequential, saying why no group formed. **The default is unchanged:** without `--concurrent` none of this applies, and `--agents` or `--no-review` alone is reported as ignored.
**`--nonstop --concurrent`:** no STOP anywhere, **no fixed groups** and so no per-group Step 4f — the rolling schedule (#3274). A member starts as soon as a slot frees and every member it depends on has merged back; the preamble returns only the first steps and a run-state file (`concurrentRun.schedule: "rolling"`, `stateFile`), and after each merge-back and each batch's reports the parent runs `node .claude/scripts/shared/lib/concurrent-orchestration.js next-steps --state <stateFile> --merged N` (or `--passed N`) and executes what it prints until `done`. A lone runnable member — no other runnable, none running — is worked inline in the tracker checkout: no worktree, member agent or merge-back, so no Merge-Back Review Gate; the parent then records `--passed N` (#3342). An output the parent lost is printed again, verbatim and read-only, by `next-steps --state <stateFile> --show-batch <id>` or `--show-start <N>` (#3349) — never by re-running `--merged`, which issues a new set. Each merge-back hands its members a batch — teardown, reconcile, the deferred skills, the commit of generated outputs, the post-merge pass over that batch's own range (`merge-back-gate.js batch-range`, then `group-tier1 --prior` for an earlier batch's members) — then their Steps 4–5 and report. The exclusive suites, the sequential tail and the run-level Step 4f follow the last batch; each member is reported as it reaches `in_review`, the nonstop summary comes at the end and repeats any leftover-worktree report — mid-run, a running member's worktree is expected there. Halts — a residual merge conflict, a failed worktree creation, a second gate fail, a dependency on a skipped `qa-required` member, an end-of-run sweep failure — follow the `--nonstop` halt contract with every worktree kept. **A finished member leaves no scratch file (#3360):** after its report its `scratch-clear` step runs `merge-back-gate.js clear-member`, removing its `.tmp-gate-<N>-*` files and `.tmp-brief-<N>.md` — its tier1 file waits until every member that ran beside it merged, since their `outcome --sibling` reads it — and after the run-level Step 4f passed, `clear-run` removes the rolling state and run ledger. Default-mode groups clear each member after the group's reports. A halt clears nothing; `clear-member` keeps all four while the member's ledgered worktree exists, so a resumed run finds them; the startup sweep is the fallback.
**A resumed `--concurrent` run (#3264)** picks up what an earlier run left instead of re-spawning it. **Finish-only members:** a member whose `Refs #N` commits already reached the tracker through a merge leaves the plan for `concurrencyPlan.finishOnly` — it gets a `resume-finish` step and then its remaining steps (Steps 4–5 and its report) over the commits already there, never a spawn, gate or merge-back; a dependency on it counts as met. When every active member is finish-only, no group forms and `noGroupReason` says so. **Held members and their dependents:** a member with a worktree kept from an earlier run — a halt keeps every worktree, and one may hold fixes — is held, not re-spawned: `concurrencyPlan.held` names it and `concurrencyPlan.heldBehind` every member that depends on it, transitively, and none of them runs this run. Each held member is warned `KEPT_WORKTREE` with its worktree path, its branch and the merge-back command (`merge-back-gate.js merge-back --tracker <tracker branch> --member N:<branch>:<path>`); check the worktree, merge it back or tear it down with `worktree-teardown.js`, then re-run. **The run ledger:** kept worktrees are matched to members through `.tmp-concurrent-<tracker>.json` at the root (`concurrentRun.ledgerFile`). Each spawn step's `onSpawned` names `node .claude/scripts/shared/lib/concurrent-orchestration.js record-spawn --ledger <ledgerFile> --issue N --branch <its wt/* branch> --worktree <its worktree path>`; the parent runs it once that member's spawn returns, and the first record creates the file — a spawn never recorded cannot be matched on resume. A `wt/*` worktree no run ledger names (or every one, when no ledger is found) is warned `UNMATCHED_WORKTREE` and matched to no member: it may hold a member's work from an earlier run, so inspect it before tearing it down.
#### Step 6a: Post-Nonstop Audit
1. `node .claude/scripts/shared/nonstop-audit.js --issue $ISSUE --processed <processed sub-issues>` (#3271 — every audit covers only those; with `groups.work` on a processed child with no events is a pairing finding; audit (6) names one with no recorded Review-State Gate decision) after all sub-issues reach `in_review`, before moving epic. Returns `{ok,warnings,blocks}` covering audit (1) commit density (warning, non-blocking, per sub-issue), audit (2) AC checkbox (blocks — require Step 4 on flagged sub-issues), audit (4) announcement pairing (warning, non-blocking — see 2a) and audit (5) doc judgment (warnings, non-blocking — an open sub-issue with no `**Doc judgment:**` line, the record Step 3b writes; closed sub-issues finished by earlier runs not audited).
2. **Audit (3) — coverage (skill):** Per sub-issue, invoke `tdd-refactor-coverage-audit` skill where sha is immediately before first `Refs #N` commit. Applies **No-Runtime Fallback Pattern (Pattern 4)**: Node 18+ → `node .claude/skills/tdd-refactor-coverage-audit/scripts/test-coverage-audit.js --since-commit <sha>` (primary); Node unavailable → follow skill's "Fallback Procedure" (read `resources/test-coverage-conventions.json`, run `git diff --name-status --diff-filter=A <sha>..HEAD`, apply pairing rules inline). Both paths emit equivalent advisory output (`newSources`, `pairedSources`, `missingTests[]`, `coverage`); never blocks. Skill absent → `"Skipped coverage audit: tdd-refactor-coverage-audit skill not installed."`, continue.
**Report the three classes separately; only two are gaps (#2865).** Since #2862 every test is `module`, `flow` or `contract` and the envelope's `classes` block carries all three. Summarize each; list as gaps **only `module.unpaired` and `flow.undeclared`**.
**The other two cannot be gaps by construction — state the reason, or the omission reads as arbitrary and the next edit restores a third bucket.** A `contract` test pairs by **declared subject**, a `flow.declared` spec by **annotation**; neither pairs by stem, so neither has an unpaired stem. Reading the flat pre-#2862 fields reports both as uncovered sources — deliberate test design flagged as a gap, scaling with the number of flow specs. **Worse than a missing warning:** audit (3) is non-blocking so it can be read at a glance, and an advisory whose false positives grow with the codebase is one nobody reads, taking the genuine `module.unpaired` findings with it.
**`coverage` is a module-class ratio; `flow.undeclared` is a count.** Never average them — full module pairing with six orphaned flow specs is not 100% covered, and one number says it is.
2a. **Audit (4) — announcement pairing (#2790).** Returned by the same `nonstop-audit.js` call as (1) and (2); no separate invocation. Reconciles the sender-side ledger for every processed sub-issue and reports as **warnings**: a `work-completed` recorded with no `work-started` (`missingOpener` — the observed defect), an opener with no closer (`missingCloser`), and any announcement composed but left `pending` or recorded `failed` (`undispatched`). A `shouldSend: false` composition (no peers, a disabled group) is recorded `skipped` at composition time with the notice as reason (#2990) and reported as a separate `skipped` count, **never** `undispatched` — nothing was meant to be sent, and counting it buried the real omission under the common case; the count keeps an all-skipped run from reading silent. All composition paths (`/work`, review events, `/done` push group, branch-operation notices) record through the same ledger call, so record-only entries share the shape. **Advisory, never blocking** — it audits a channel that gates nothing, and an audit stricter than the thing it audits is a gate by the back door. `status: "skip"` means no ledger exists here: messaging may be disabled, or the run predates the ledger. **Skip is not a pass and not a failure** — nothing was recorded, so nothing can be reconciled, and reporting dropped openers there trains the reader to ignore the audit. Relay `caveats` verbatim: the ledger is project-scoped with no per-session form, so entries from two concurrent sessions cannot be separated afterwards and the audit says so rather than implying it isolated one run.

2b. **End-of-run sweep (#3202).** Under `--nonstop` Step 4f runs once, after the last sub-issue and before this audit. A failure is **blocking**, reported beside audit (2) with Step 4f's attribution (failing suites and tests, the sub-issues whose changed files they cover, or `unattributed`); processed sub-issues stay `in_review`.
3. Aggregate audit output. Proceed to epic `in_review` move only after audit (2) blocks and an end-of-run sweep failure are cleared — (1) and (4) are warnings and clear nothing.
4. **A `--concurrent` run is audited exactly as a sequential one (#3139).** Every member fired its gates and events once and carries its own `Refs #N` set, so audits (1), (2) and (4) read ledger and commits with no concurrent-specific path. The summary adds the leftover-worktree report repeated from each group's check (`leftoverWorktrees()`) and — under `--no-review`, or with the `diff-review` skill absent — the Tier 3 skips named per member, so a run whose merges rested on Tiers 1–2 alone is distinguishable from one independently reviewed. A halted member keeps its worktree; the audit names it rather than counting it processed.
