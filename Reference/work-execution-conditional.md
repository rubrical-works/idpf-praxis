### Step 1b: Epic Complexity Assessment
Trigger: `context.type=="epic"` and `--nonstop`. `node .claude/scripts/shared/epic-complexity.js $ISSUE`. `classification=="functional"` → `strictTDD=true`. Signals: `.claude/metadata/epic-complexity-signals.json`.
### Step 2b: Prime Sub-Issue Task List (epic/branch)
Trigger: `context.type in {epic, branch}`. After Phase 2, take the active set from the **envelope Step 1 already parsed** — no CLI call. `context.subIssues` is the full child list (active plus skipped, body/label-enriched per #2622), `context.skipped` is `[{number, status}]` (plus `reason: 'qa-required'` on a label skip, below), so active = `subIssues` minus `skipped`: a complete partition at zero extra round trips. For each remaining, in `context.resumeOrder` order (#3270), `TaskCreate` subject `Sub-issue #N: $TITLE` with description `Per-sub-issue parent — owns AC subtasks and this sub-issue's turn of Steps 3, 3-i, 3-ii, 3-iii, 3b, 4, 4a, 4b, 4d, 4e, 4c, 4f (default mode), 4g, 5.` Parents make compaction-recovery resume self-describing: `TaskList` alone shows active sub-issue.
**A `qa-required` sub-issue is skipped with a pointer, never redirected mid-loop (#2824).** Signal: `context.subIssues[].labels`, fetched by the same status query; `checkSubIssueStatuses` places such a child in `context.skipped` with reason `qa-required` — `{ number, status, reason: 'qa-required' }` — whatever its board status, so the active set excludes it and no parent task is created. Report each at its turn as `Sub-issue #N is qa-required → run /qa #N` and count it in the final `Nonstop Processing Complete` summary. A mid-loop `Skill("qa", …)` redirect was rejected: Skill *transfers control*, `/qa` ends at its own STOP, and nothing returns to the sub-issue loop — remaining sub-issues are silently never processed and the summary never prints. QA sub-issues are gates on the *parent's* closure, not work in sequence with siblings, so the loop loses nothing. The `/qa` redirect is single-issue only. `test-plan` sub-issues share the latent mid-loop gap — #2784's surface, not claimed here; the skip is written to carry a second label.
**Do not re-query — and do not "repair" the old call either (#2751).** This step previously instructed `gh pmu sub list $ISSUE --json=number,title,status` then an `in_review`/`done` filter. Neither half worked, and the second is why re-querying stays wrong even corrected:
| Half | What actually happens |
|---|---|
| the call | **Errors.** `--json` is **boolean** on this subcommand and takes no value: `strconv.ParseBool: parsing "number,title,status": invalid syntax` |
| the filter | Even in the working form the output carries **no board status**. Children carry `number, title, state, url, repository`; `state` is GitHub `OPEN`/`CLOSED`, never `in_review`/`done`. An issue can be `in_review` while still `OPEN`, so the filter is **underivable** from this output |

Working form is the bare flag `gh pmu sub list $ISSUE --json`, returning `{issue, children, summary}` — an object with a nested `children` array, not the flat array "for each remaining" implied. Board status needs one `gh pmu view $N --json=status --jq='.status'` per child.
`work-preamble.js` already does both in exactly those forms — `loadSubIssues()` calls the bare form and maps `result.data.children`; `checkSubIssueStatuses()` runs the per-child view and returns `{skipped, active}`. The run has already paid for this fact; re-deriving it here creates a **second** source of truth, and the second source is the one that drifts.
### Step 2b-ii: Tree-Wide Review Gate (epic — #2748; branch tracker + `--nonstop` — #2749)
**Trigger:** `context.type == "epic"` (#2748), `context.type == "branch"` with `--nonstop` (#2749), or a **non-epic selection of two or more issues** (#2750) — `/work 44 47 68`, `/work --status ready`. A single-issue selection (`/work 44`) runs Step 3's resident Review-State Gate instead, which classifies the one member the same way. A branch tracker without `--nonstop` skips this step and is gated per sub-issue at Step 3. Reasoning: rationale file § Step 2b-ii.
**The selection gate (#2750).** A typed selection is classified **in full** before the first acceptance criterion of its first member, and raises **one** question over the whole selection. The per-issue actions in `.claude/metadata/review-state-gate-actions.json` are unchanged.
- **N=1** is Step 3's path, per `.claude/metadata/review-state-gate-actions.json`: for `never-reviewed` and `stale-reviewed` `/work` reviews the issue itself through one reviewer agent, `--step-wise`, no status move, proceeding on `reviewed` (#3537); `findings-pending` STOPs and offers `/resolve-review`.
- **At N ≥ 2 a third option drops the flagged members**, and the run reports which were dropped and why. It is not offered at N = 1, or when every member is flagged — it would proceed with nothing.
- **`--status <status>` selections are covered**, whatever their size: one `gh issue view` per member, no size threshold.
- **A selection bypass is never recorded** — a selection has no container issue. The decision holds for the invocation, compaction included.
**Two gates on a branch tracker under `--nonstop` (#2749):**
| | Runs | Scope | Owns |
|---|---|---|---|
| **Step 2b-ii** | once, before the first sub-issue | the whole processable set | whether this unattended run may proceed at all |
| **Step 3 Review-State Gate** | per sub-issue, at its turn | one issue | the per-issue decision; the safeguard for a member Step 2b-ii never saw |
Step 2b-ii runs first, so Step 3 does not re-prompt for a member it decided. Step 3 still catches a sub-issue added after Step 2b-ii ran, or a run resumed after compaction into the middle of the set.
**Three enumerations, one decision (#2748, #2750):**
| Gate | Enumerates | Tracker classified? | Drop option? |
|---|---|---|---|
| Epic (#2748) | the epic **plus** every child of `gh pmu sub list` | **yes** — an epic has its own ACs and review label | no |
| Branch tracker + `--nonstop` (#2749) | the processable set of children | **no** — nothing reviews a branch tracker | no |
| Selection, 1..N (#2750) | argv, or the `--status` query result | n/a — no tracker | **yes, at N ≥ 2** |
**Only a hand-typed selection may drop** (#2780). All three resolve states with `review-state.js` and hand an already-resolved list to `branch-review-gate.js`. The differences are carried as caller data — `isTracker` per member, `setShape` for the set — never as an issue-type test inside the helper.
**Scope is the processable set:** members already `in_review` or `done` are removed and the preamble's `skipped[]` is honored, so the classified set matches what Step 6a will iterate. An unreviewed member the run will never reach is not a reason to stop.
**Run the script; do not re-derive its steps (#2826).** Enumeration, per-child board status, classification and aggregation all live in `.claude/scripts/shared/tree-review-gate.js`, a runner around `lib/branch-review-gate.js`:
```bash
node .claude/scripts/shared/tree-review-gate.js --issue $ISSUE [--tracker] [--skipped '<context.skipped as JSON>']
```
`--tracker` declares a branch-tracker root `isTracker: true`; an epic run omits it. `--skipped` is the preamble's `context.skipped` verbatim. `setShape` is `'tree'` for both, which withholds the drop option. Read `data`: `gate`, `options`, `neverReviewed`, `staleReviewed`, `findingsPending`, `indeterminate`, `processable`, `toReview`, `reviewCount`, `pendingOptions`, `relabeled`, `members` (each `number`, `title`, `state`, `boardStatus`, `isTracker`).
**Name every relabel in the run report (#3715).** Report each `data.relabeled` entry (`{number, removed, added}`) as `#N relabeled reviewed → pending (stale review)`, beside the preamble's `gates.relabeled`. Members in `--skipped`, In review or Done are classified read-only and keep their label.
**Review first (#3537).** `toReview` is every never-reviewed or stale-reviewed member — an epic included, a branch tracker never. When it is non-empty, report `reviewCount` before any review runs. Review each as Step 3's `review` action does: one Agent from `node .claude/scripts/shared/lib/issue-reviewer-brief.js --issue N` (`--stale` for a member in `staleReviewed`), always `--step-wise`, no status move. A failed review stops the run, never counted as clean. Then re-run this script; what is left to decide is `findingsPending`.
**One decision for the pending members.**
1. `data.gate: false` → proceed silently.
2. `data.gate: true` with `findingsPending` non-empty → **one** `AskUserQuestion` naming them, offering `pendingOptions`:
   - `resolve-now` — hand off to `/resolve-review` naming every pending member (`/resolve-review #A #B`) and **STOP**, every issue as found; re-run `/work` once they are `reviewed`.
   - `exclude` — a selection of two or more only — drop them and report which.
   - `stop` — end the run.
3. No decline proceeds: only `--unreviewed` waives the gate, and the run report names each waived issue and its state.
4. Under `--nonstop` a member still `findings-pending` after the review **halts** the run instead of asking.
5. Never re-ask within the invocation, compaction included. Relay `warnings` verbatim.
**Two failure modes.** `ok: false` with `ENUMERATION_FAILED` → **STOP and report**; a gate whose scope call errors would pass vacuously. A failed read of one *member* fails open: that member is `indeterminate` or keeps a null `boardStatus` and stays processable, with a warning naming it, and never prompts.
**The selection gate rides the same script:** `node .claude/scripts/shared/tree-review-gate.js --issues "44,47,68"` classifies the argv members, declares `setShape: 'selection'` and so offers `proceed-with-clean` at N ≥ 2, with `data.clean` naming who would proceed. `proceed-with-clean` (in `options`, before any review) and `exclude` (in `pendingOptions`, after `/work` has reviewed) are the same drop at two moments; the question asked offers `pendingOptions`. A `--status <status>` selection passes the query result the same way.
**On decline the run STOPs and nothing is recorded**, for every shape:
| Type | What `tree-review-gate.js … --record-bypass` would do |
|---|---|
| **Epic** | write a dated note into the epic body naming the flagged members (idempotent: `written: false, reason: already-recorded`) |
| **Branch tracker** | nothing — `--record-bypass --tracker` reports `reason: branch-tracker` |
| **Selection** | nothing — reports `selection` |
No decline continues, so `--record-bypass` has no caller in this workflow (#3682). **No recorded note suppresses the gate on a later run** (#2748 AC8): `review-state.js` reads labels and the `**Reviews:** N` marker only.
### Step 2c: Proposed Work Order (`--nonstop` epic/branch — #2622)
Trigger: `context.proposedOrder` present. The preamble sets it only for `context.type in {epic, branch}` under `--nonstop`; absent in every other mode, so this step does not fire.
**Report before the first sub-issue is worked — four inputs, one report (#3128):**
| Input | Source | Status |
|---|---|---|
| **Graph order** | `context.processingOrder` vs `context.declaredOrder`, edges from `context.dependencyGraph` | **Applied** — `**Depends on:**` is explicit, so the run already works in this order; report where it differs from declared and name each edge that moved a member |
| **Heuristic suggestion** | `context.proposedOrder`, suggested edges in `context.orderRationale`, from `review-interdependence.js` | **Proposed** — never applied without acceptance |
| **Concurrency groups** | `context.concurrencyPlan` (`--concurrent` only) — groups by layer, each at most `--agents N` (cap on agents of any kind, default 3), then the tail with causes; whether `--no-review` will skip the gate's Tier 3 | **Derived** from the graph order; a zero-group plan falls back to sequential |
| **Worktree base** | `context.concurrencyPlan.worktreeBase` (`--concurrent` only) — `{ registered, layer, base }`: `base` is `tracker tip` when a settings layer registers the WorktreeCreate hook (`layer` = first one: `project`, `project-local`, `user`), `sequential fallback` when none does | **Reported** in both cases on a `worktrees:` line beside `groups:` — a registered hook is told apart from a decision never made |
```
Work order for #$ISSUE:
  declared: #901 → #902 → #903
  graph:    #902 → #901 → #903   (#901 depends on #902)
  proposed: #902 → #903 → #901
    #903 creates declared scope src/order-helper.js that #901 also declares — provider should precede consumer
  groups:   [#902, #903] → [#901]; tail: none
  worktrees: tracker tip (WorktreeCreate hook registered in the project layer)
```
Hook absent → `worktrees: sequential fallback (no settings layer registers the WorktreeCreate hook)`.
**A proposal can never place a member before what it depends on** — the preamble re-sorts the heuristic topologically, so it only breaks ties the graph leaves open. The scope heuristic once proposed a story ahead of the one its own `**Depends on:**` named, reading "created in #N" as the story creating the file; a declared edge outranks inference from prose.
`context.orderDiffers==false` → report the proposal matches the order in effect, continue; nothing to decide.
**Ask once, then persist — only on acceptance.** Orders differ → offer **one** `AskUserQuestion`: accept proposed, or keep the order in effect. On acceptance write it to the tracker body via `gh pmu view $ISSUE --body-stdout` → `applyProcessingOrder(body, acceptedOrder)` → `gh pmu edit $ISSUE -F` → `rm`. On decline **nothing is written**; the run proceeds in `context.processingOrder` — the graph order, which a decline does not undo: its dependencies are declared, not proposed. The preamble never writes — `applyProcessingOrder` returns a new body and the caller persists it, which is what keeps the decision reviewable.
> **Why propose rather than apply (#2622):** the derivation is deterministic but demonstrably incomplete — measured over #2614–#2620 it surfaced one of two real declared-scope collisions and reported 21 boilerplate `sharedCriteria` matches. `--nonstop` removes the per-sub-issue STOP where a human would otherwise catch a wrong order, so a silent reorder would replace a knowably-wrong order with an unaccountably-wrong one, unattended. Surfacing costs one question; getting it silently wrong costs a sub-issue implemented against a provider that does not exist yet.
> **Why persistence reuses `**Processing Order:**`:** an accepted order must survive compaction, and that format is already parsed by `parseProcessingOrder` (#2544). The next run — this one resumed, or a later one — reads it through the mechanism that already exists, with no new state store to keep in sync.
### Step 3: `--concurrent` Test Scope and the Merge-Back Review Gate (#3117)
**Trigger:** `--concurrent` on an epic, a branch tracker or a selection of two or more issues (#3681; Step 1d loads this file for those shapes).
**Under `--concurrent`, the `--agents` cap is also the unit-test concurrency cap (#3132).** Each member of a group runs its scoped suites inside its own worktree, so at most `--agents` test runs execute at once — and only suites a member may run there: `scopedInvocations({inWorktree: true})` returns the `parallel` suites and defers the `exclusive` ones (`e2e` by role default, or declared). The parent runs the deferred set through `deferredInvocations()` once per group, serially, on the tracker branch after merge-back, worktree teardown **and reconciliation** (#3272 — the deferred skills run first too, so these suites test the reconciled tree), scoped to the union of the group's changed files, regenerated paths included — never inside a worktree, never skipped. Neither that run nor Step 4f starts while a worktree of the group exists; `leftoverWorktrees()` names any `.tmp-wt-*` still under the root and the run continues.
**Merge-Back Review Gate outcomes (#3130, #3141).** Before a member's branch merges back, `merge-back-gate.js` runs three tiers: Tier 1 (mechanical — `Refs #N` on every commit, nothing uncommitted, scope drift, the member's parallel suites in its worktree), Tier 2 (the parent's own file-by-file read; the direct-work exemption never applies) and Tier 3 (an independent `diff-review` reviewer, never handed the implementer's summary). `--no-review` skips Tier 3 and an absent skill degrades to Tiers 1–2 — both reported, never silent.
**Which suites Tier 1 runs before merge (#3730):** every `parallel` suite whose scoped command narrows to the member's changed files (`scoped.mode: path` with a `{files}` command, a linter included once it declares one) runs in the member's worktree; a failure fails Tier 1 naming the suite and its command, so `outcome` never returns `merge` and the one fix cycle goes to the implementer. A suite that cannot narrow, and every `exclusive` suite, waits for the post-merge pass on the tracker: Tier 1 lists it in `deferredSuites` with a `note` saying it was not run before merge. A suite opts in by declaring a narrowed command.
1. **The reviewer writes its own review (#3204)** to `.tmp-gate-<N>-tier3.json`, the one file it may write; the parent never saves or re-words its reply. The parent runs `tree-snapshot --clear .tmp-gate-<N>-tier3.json` before the spawn, which removes any earlier cycle's review.
2. `outcome --tree-before` fails Tier 3 as `tier-3-missing` when the file is absent, as `tier-3-stale-output` when the snapshot already listed it, or as `tier-3-wrote-outside-contract`, naming the paths, when anything outside this member's own review and snapshot and its running-group siblings' own gate files changed (#3220).
3. **Scoped to the run (#3263):** when every running member's Tier 1 document names its declared scope, only a change inside those `runPaths` fails; a change outside them is listed as `external` (another session's) and reported, never failed — with any scope unreadable the check stays strict.
   **A ledgered member's worktree is the run's own (#3729):** under the rolling schedule the parent spawns the next member, or tears a merged one down, while a sibling's reviewer runs. `gate-outcome` passes `outcome --ledger <the run ledger>`; a worktree directory the ledger (`.tmp-concurrent-<tracker>.json`, written by `record-spawn`) names that appeared or disappeared during the review is reported as `tier3.runWorktrees` (`appeared`, `removed`), never failed. A `.tmp-wt-*` directory no run ledger names still fails as `tier-3-wrote-outside-contract`; no `--ledger`, or an unreadable one (`tier3.ledgerError`), exempts nothing. Run `record-spawn` as each spawn returns, before any sibling's `outcome`.
4. **The merge comment needs no file (#3276):** `outcome --post-comment` posts `comment.body` through `gh issue comment --body-file -` on stdin, writes no root file, and returns `posted` (issue, comment id, url) or `postError` (exit 1). The snapshot check is the enforcement: the Agent tool has no per-spawn write restriction.
5. **The Tier 1 document is verified the same way (#3225):** `tier1 --out .tmp-gate-<N>-tier1.json` writes it and reports the sha256 of the bytes it wrote, and `outcome` requires `--tier1-sha`; it too sits in the reviewer-writable root, so a file changed since halts as `tier-1-document-changed`, naming the file, and the member is never merged.
6. **Pass or warn merges** the member and posts the findings as a structured comment on the sub-issue.
7. **A fail buys exactly one fix cycle:** `decideOutcome` sends the findings to the same implementer by `SendMessage` with its worktree intact, every tier re-runs once, and **a second fail halts** under the `--nonstop` contract with files and lines, the worktree kept, the member never merged.
8. **A reviewer-process failure is a re-review, not a fix cycle (#3222):** with Tier 1 passing, a Tier 3 `tier-3-missing`, `tier-3-wrote-outside-contract`, `tier-3-stale-output` or `tier-3-snapshot-changed` yields `re-review` — the parent re-snapshots, re-spawns the reviewer in the same slot and re-runs `outcome --review-retries 1`; the implementer's fix cycle is not spent on it, and a second such failure halts attributed to the reviewer.
9. **A re-review never re-baselines over the stray writes (#3226):** after `tier-3-wrote-outside-contract` the `re-review` decision carries the named paths as `outsideContract`, and the parent reports and clears them before re-snapshotting — removing or restoring what this run wrote, and waiting for another session to settle a path it is editing, never deleting or reverting that session's work — so the paths cannot become part of the new baseline.
10. Compaction mid-cycle: the parent re-reads the worktree branch and the resumed re-run of all tiers **is** the one cycle (`resumeFixCycle`).
11. After the group's merge-back and reconciliation, Tiers 1–2 run once more in the parent over the members' diffs ∪ the runner's regenerated paths (`postMergeSet`) before the group is reported; a fail there halts on the same terms.
12. **Reconciliation's outputs have a commit rule (#3272):** after the deferred skills, `regenerateAfterSkills` re-runs every generator that reads their outputs (the extension registry, after `fw-minimize-files` rewrites `.claude/commands/**`), and every path the reconcile, deferred-skills and that pass rewrote is committed once as `Refs #<root>` — the epic, or the branch tracker's own issue — then passed to `group-tier1` as `--regenerated` with `--epic <root>`.
13. **Two group members changing the same file outside their declared scope halt merge-back before any merge** (`undeclared-overlap`, every member named), and `group-tier1` repeats the check over members' own commits; one member's out-of-scope path stays advisory (#2520) and is listed in its merge comment.
### Step 4f: Cadence under `--nonstop` (epic or branch tracker — #3202)
**Trigger:** `--nonstop` on an epic or branch tracker.
Each sub-issue's boundary is covered by its scoped tests (Step 3) and it moves to `in_review` without a full sweep; **one** full sweep — every run `sweepInvocations()` returns, reported per suite as rule 08 Step 4f directs — runs after the last sub-issue, before Step 6a, over the union of every processed sub-issue's changed files. Under `--concurrent` the per-group sweep gives way the same way: `buildRun()` emits a single run-level `4f` step after the last member. The shared Step 4f task is marked `completed` after that sweep.
**On a failure, halt under the `--nonstop` contract and attribute it:** name each failing suite and test and, from the changed-file union, the sub-issues whose changed files those tests cover — a test file the sub-issue changed, or a source file it changed that the test exercises; when neither holds say `unattributed`, never guess. Processed sub-issues stay `in_review` — none is moved back — and the Step 6a summary reports the sweep failure as **blocking**: commit the fix under the attributed sub-issue's `Refs #N` and re-run the sweep.
**A `--nonstop` halt before that sweep** — a failed worktree creation, a residual merge conflict, a second gate fail, any halt after at least one sub-issue reached `in_review` — leaves those sub-issues unswept: the halt report names them (`Not swept`, from `haltReport`'s `unswept` list and `merge-back --unswept`), and they must be swept before `/done`, because a resumed run skips `in_review` members. **Default mode is unchanged:** a per-sub-issue STOP keeps its per-sub-issue sweep.
### Step 4g: Independent Review (#3457)

**Trigger:** every issue, after Step 4f and before Step 5 — the resident directive in rule 08 runs `review-plan`; this is what to do with its result. Under `--concurrent`, a group member's review **is** the Merge-Back Review Gate's Tier 3 (§ Step 3), so Step 4g runs only for the sequential tail and for a lone member worked inline.

**Plan.** `node .claude/scripts/shared/lib/merge-back-gate.js review-plan --issue $ISSUE`, adding `--nonstop` and `--no-review` when the run has them. It resolves `workReview` through `framework-config.js` `resolveWorkReview()` — `always` when absent, `nonstop-only`, or `off` — and the issue's own `Refs #$ISSUE` commits since the branch's merge-base, and returns `review`, one of two things:
- **A reported skip** (`skipped: true`, `reason` one of `no-review`, `work-review-off`, `work-review-nonstop-only`, `no-commits`, `skill-absent`): report its `message` and continue to Step 5. A skip is never a pass, and never silent.
- **The Tier 3 reviewer request** the Merge-Back Review Gate uses: the issue's commit range and its own commits (another issue's commits can sit inside the range), its ACs, its `Files to modify:` and the charter — never the implementer's summary.

**Review.** `node .claude/scripts/shared/lib/merge-back-gate.js tree-snapshot --out .tmp-gate-$ISSUE-tree-before.txt --clear .tmp-gate-$ISSUE-tier3.json`, then spawn **one** read-only Agent as `review.request.subagent_type` (`idpf-diff-reviewer`, #3507) with `review.request.prompt` verbatim — a type not found follows `review.request.onNotFound` — the brief carries the code and the ACs, nothing you summarize. It writes `.tmp-gate-$ISSUE-tier3.json` and nothing else. Then `node .claude/scripts/shared/lib/merge-back-gate.js review-outcome --issue $ISSUE --tier3 .tmp-gate-$ISSUE-tier3.json --tree-before .tmp-gate-$ISSUE-tree-before.txt --tree-before-sha <sha256 tree-snapshot reported> --post-comment`, adding `--fix-cycles 1` or `--review-retries 1` on a re-run. **The tree check is scoped to the issue's declared scope:** another session's write outside it during the review is reported as `external`, never failed; a write inside it fails the review as `tier-3-wrote-outside-contract`.

**Act on `action`:**
| `action` | Do |
|---|---|
| `proceed` | `pass` or `warn`: the `## Work Review` comment is posted (`posted`; report a `postError`). Continue to Step 5 |
| `fix` | The one fix cycle: fix each finding in a `Refs #$ISSUE` commit, re-run Steps 4c and 4f (under `--nonstop`, the scoped tests), re-run `review-plan` — the first plan's range ends before the fix commits — then re-snapshot, re-spawn with the new plan's prompt and re-run `review-outcome --fix-cycles 1` |
| `re-review` | A reviewer-process failure, not a finding: report and clear any `outsideContract` paths this run wrote, re-snapshot, re-spawn and re-run with `--review-retries 1` — no re-plan, since no commit was added. The fix cycle is not spent |
| `halt` | Report `report` and STOP before Step 5; the issue stays `in_progress`. Under `--nonstop` this is a halt under the `--nonstop` contract |

After `proceed`, remove the scratch with `node .claude/scripts/shared/lib/merge-back-gate.js clear-member --issue $ISSUE`.

**Cadence under `--nonstop`:** once per sub-issue, before that sub-issue's Step 5 — each range stays inside the reviewer's read budget, and a finding is attributed to the sub-issue that made it. The end-of-run sweep (§ Step 4f) does not wait for it, and it does not wait for the sweep.

**Compaction:** `tree-snapshot --clear` removes a review file from before compaction; re-run the review. A `Refs #$ISSUE` fix commit already made after a `fix` decision means the cycle is spent — re-run with `--fix-cycles 1`.

### Step 6: `--nonstop` and `--concurrent` Processing
**Trigger:** `--nonstop` or `--concurrent` on an epic or branch tracker, or `--concurrent` on a selection of two or more issues (#3681).
**`--nonstop` mode:** same cycle as default mode, **no STOP** between sub-issues. Report `"Sub-issue #N: $TITLE → In Review (M/T processed)"`, continue. Ignored for standard issues. Step 4f runs once at the end of the run, not per sub-issue (§ Step 4f above). One commit/AC (`Refs #N`); commits local (push deferred to `/done`). Test/AC/QA/`gh pmu` failure halts immediately — report which sub-issue, count completed, resume instructions. A `findings-pending` verdict from the Step 3 Review-State Gate halts on the same terms (#2577). **Post-compaction:** re-read rule; `TaskList` — the `in_progress` sub-issue parent task (per Behavior Rule 7) is the primary resume signal. If no parent is `in_progress`, fall back to re-running the Step 1 preamble and resuming from the first member of `context.resumeOrder` — the dependency order, `context.processingOrder` minus `context.skipped` (#3270) — **not** to `gh pmu sub list $ISSUE` alone, which carries no board status (#2751): an `in_review` issue is still `OPEN`, so resuming on that signal re-works a sub-issue already finished. Final: `Nonstop Processing Complete` (processed/skipped/failed).
**A sequential halt is recorded on the tracker (#3270).** When a `--nonstop` run halts after any sub-issue reached `in_review` and before the end-of-run Step 4f, post a tracker comment carrying `buildUnsweptMarker(<those members>)` (`<!-- unswept: #a, #b -->`, `work-preamble.js`). A resumed `--nonstop` run returns it as `context.unswept`: the end-of-run Step 4f covers those members' changed files with its own, and once it passes, post `buildUnsweptMarker([])` to clear it.
**`--concurrent` mode (#3117):** on an epic, a branch tracker or a selection (below), file-disjoint members whose `**Depends on:**` edges are met run at once in framework-owned worktrees, in groups of at most `--agents N` (default 3 — the cap on agents of any kind at once, reviewers and fix cycles included, and on unit-test concurrency); everything else falls to a sequential tail worked as standard `/work`. **Member worktrees are created by the framework's `WorktreeCreate` hook at the tracker tip** (`.tmp-wt-*` on `wt/*`), so Claude Code's `worktree.baseRef` does not apply; the preamble verifies the hook is registered and falls back to sequential without it (#3224), reporting its decision in `concurrencyPlan.worktreeBase` (#3568).
The parent owns every gate, event, merge-back and status move; each member agent owns Step 3 in its worktree. Before merge-back the Merge-Back Review Gate runs (§ Step 3 above); `--no-review` skips its Tier 3, reported. **One STOP per group**, after merge-back with every member `in_review`; the tail STOPs per member. **Fallback:** a plan with **zero groups** runs exactly as sequential, saying why no group formed. **The default is unchanged:** without `--concurrent` none of this applies; `--agents` alone is reported as ignored, and `--no-review` alone skips the sequential Step 4g review, reported (§ Step 4g, #3457).
**`--concurrent` on a selection (#3681):** `/work #A #B --concurrent`, `--issues "A,B" --concurrent` and `--status <status> --concurrent` plan the selection exactly as a tree's members: the batch envelope carries `concurrencyPlan` and `concurrentRun` at its top level, and members merge back onto the **current branch's tracker** (`concurrencyPlan.tracker`), which is also the run's `<root>`.
- The members are the **workable** ones — `ok` and not redirected — in selection order, with `**Depends on:**` edges among them placing them across groups; a dependency on an issue outside the selection is a non-member entry, never treated as satisfied, so that member falls to the tail as `unresolved-dependency`, as for an epic.
- A redirected member (`test-plan`, `qa-required`) and a failed one (`TREE_IN_BATCH` among them) are listed in `concurrencyPlan.excluded` and never spawned; the redirected are reported with their command at the end.
- **The selection review gate runs first:** `concurrentRun.steps[0]` is the `selection-review-gate` step — Step 2b-ii's gate over every planned member before any spawn; a member it stops or excludes is re-planned out with `replan --stopped N`.
- **Its state files are keyed `<tracker>-selection`** (`.tmp-concurrent-<tracker>-selection.json`, `.tmp-run-…`), never the tracker-rooted run's, so a resumed selection run on that branch finds its own kept worktrees.
- **No plan, sequential:** fewer than two workable members warns `CONCURRENT_IGNORED`; no open tracker for the branch warns `CONCURRENT_NO_TRACKER` (create or switch to a tracked branch).
- A `**Depends on:**` cycle among members fails the selection with `DEPENDENCY_CYCLE`.
- `--nonstop` stays `NONSTOP_IGNORED` on a selection, so the run keeps fixed groups and one STOP per group.
**`--nonstop --concurrent`:** no STOP anywhere, **no fixed groups** and so no per-group Step 4f — the rolling schedule (#3274).
1. A member starts as soon as a slot frees and every member it depends on has merged back; the preamble returns only the first steps and a run-state file (`concurrentRun.schedule: "rolling"`, `stateFile`), and after each merge-back and each batch's reports the parent runs `node .claude/scripts/shared/lib/concurrent-orchestration.js next-steps --state <stateFile> --merged N` (or `--passed N`) and executes what it prints until `done`.
2. A lone runnable member — no other member runnable and none running — is worked inline in the tracker checkout: no worktree, no member agent, no merge-back and so no Merge-Back Review Gate; the parent records it with `--passed N` once reported (#3342).
3. An output the parent lost is printed again, verbatim and read-only, by `next-steps --state <stateFile> --show-batch <id>` or `--show-start <N>` (#3349) — never by re-running `--merged`, which issues a new set.
4. Each merge-back hands its members a batch — teardown, reconcile, the deferred skills, the commit of generated outputs, the post-merge pass over that batch's own range (`merge-back-gate.js batch-range`, then `group-tier1 --prior` for an earlier batch's members) — then their Steps 4–5 and report.
5. The exclusive suites, the sequential tail and the run-level Step 4f follow the last batch; each member is reported as it reaches `in_review`, the nonstop summary comes at the end and repeats any leftover-worktree report — mid-run, a running member's worktree is expected there.
6. Halts — a residual merge conflict, a failed worktree creation, a second gate fail, a dependency on a skipped `qa-required` member, an end-of-run sweep failure — follow the `--nonstop` halt contract with every worktree kept.
7. **A finished member leaves no scratch file (#3360):** after its report, each member's `scratch-clear` step runs `merge-back-gate.js clear-member`, removing its `.tmp-gate-<N>-*` files and `.tmp-brief-<N>.md` — its tier1 file waits until every member that ran beside it has merged, since their `outcome --sibling` reads it — and once the run-level Step 4f has passed, `clear-run` removes the rolling state and the run ledger.
8. Default-mode groups clear each member after the group's reports. A halt clears nothing, and `clear-member` keeps all four files while the member's ledgered worktree still exists, so a resumed run finds them; the startup sweep is the fallback.
**A resumed `--concurrent` run (#3264)** picks up what an earlier run left instead of re-spawning it.
- **Finish-only members:** a member whose `Refs #N` commits already reached the tracker through a merge leaves the plan for `concurrencyPlan.finishOnly` — it gets a `resume-finish` step and then its remaining steps (Steps 4–5 and its report) over the commits already there, never a spawn, gate or merge-back; a dependency on it counts as met. When every active member is finish-only, no group forms and `noGroupReason` says so.
- **Held members and their dependents:** a member with a worktree kept from an earlier run — a halt keeps every worktree, and one may hold fixes — is held, not re-spawned: `concurrencyPlan.held` names it and `concurrencyPlan.heldBehind` every member that depends on it, transitively, and none of them runs this run.
- Each held member is warned `KEPT_WORKTREE` with its worktree path, its branch and the merge-back command (`merge-back-gate.js merge-back --tracker <tracker branch> --member N:<branch>:<path>`); check the worktree, merge it back or tear it down with `worktree-teardown.js`, then re-run.
- **The run ledger:** kept worktrees are matched to members through `.tmp-concurrent-<tracker>.json` at the root (`.tmp-concurrent-<tracker>-selection.json` for a selection run — `concurrentRun.ledgerFile`).
- Each spawn step's `onSpawned` names `node .claude/scripts/shared/lib/concurrent-orchestration.js record-spawn --ledger <ledgerFile> --issue N --branch <its wt/* branch> --worktree <its worktree path>`; the parent runs it once that member's spawn returns, and the first record creates the file — a spawn never recorded cannot be matched on resume.
- **A spawn step's `onReturn` names a run template (`member-result`, #3502):** render it with `{{n}}` = the step's issue and run it when the member returns, before its merge-back — a result failing `implementer-result-schema.json` holds that member's merge-back and nothing else.
- **The `spawn-not-found` run template (#3500) applies to every spawn step:** follow it when an Agent call fails with `Agent type 'idpf-implementer' not found`.
- **The run's `specialistNotice` (#3501)**, when set, says no project specialist could be used — no specialist configured, an announce-only role, or a missing file: report it once for the run, never per member.
- A `wt/*` worktree no run ledger names (or every one, when no ledger is found) is warned `UNMATCHED_WORKTREE` and matched to no member: it may hold a member's work from an earlier run, so inspect it before tearing it down.
- **A worktree holding nothing is reclaimable (#3714):** a `.tmp-wt-*` worktree on a `wt/*` branch that is an ancestor of the tracker tip, with a clean tree (untracked included), is warned `RECLAIMABLE_WORKTREE` instead, ledger-recorded or not — an empty one from a cancelled run, or a merged member kept after a denied teardown. Never held; listed in `concurrencyPlan.reclaimable`. Commits off the tracker or a dirty tree (a held member of a halted run) is never offered and stays reported as above.
- **The reclaim offer is the run's first decision, before any spawn** (after a selection's review gate): the `reclaim-offer` step. Ask once with `AskUserQuestion`, naming each worktree — offer, never force. Accepting runs its `accept` command, `merge-back-gate.js reclaim`: re-checks each worktree, tears it down through `worktree-teardown.js`, deletes its `wt/*` branch with `git branch -d`, and for a recorded member clears its kept `.tmp-gate-<N>-*` files and `.tmp-brief-<N>.md`; report each result. Declining runs nothing.
#### Step 6a: Post-Nonstop Audit
1. Run `node .claude/scripts/shared/nonstop-audit.js --issue $ISSUE --processed <the sub-issues this run processed>` (#3271 — every audit then covers only those; `groups.work` decides whether a processed child with no events is a pairing finding; audit (6) names a processed child with no recorded Review-State Gate decision) after all sub-issues reach `in_review`, before moving the epic. Returns `{ ok, warnings, blocks }` covering audit (1) commit density (warnings, non-blocking, per sub-issue), audit (2) AC checkbox (blocks — require Step 4 on flagged sub-issues), audit (4) announcement pairing (warnings, non-blocking — see 2a) and audit (5) doc judgment (warnings, non-blocking — an open sub-issue whose body has no `**Doc judgment:**` line, the record Step 3b writes; closed sub-issues finished by earlier runs are not audited — #3176).
2. **Audit (3) — test coverage (skill-delegated):** For each processed sub-issue, invoke the `tdd-refactor-coverage-audit` skill via the Skill tool, where `<sub-issue-start-sha>` is the SHA immediately before the first `Refs #N` commit for that sub-issue (derivable via `git log --grep="Refs #N" --format=%H | tail -1` then `git rev-parse <sha>~1`). The skill applies the **No-Runtime Fallback Pattern (Pattern 4)**: if Node 18+ is available, run `node .claude/skills/tdd-refactor-coverage-audit/scripts/test-coverage-audit.js --since-commit <sub-issue-start-sha>` (primary path). If Node is unavailable, follow the skill's "Fallback Procedure" section — read `resources/test-coverage-conventions.json`, run `git diff --name-status --diff-filter=A <sub-issue-start-sha>..HEAD` via the Bash tool, apply pairing rules inline. Both paths emit equivalent advisory output (`newSources`, `pairedSources`, `missingTests[]`, `coverage`); warnings are advisory (non-blocking, consistent with the per-cycle REFACTOR usage at `tdd-checklist.json:36`). If the skill is not installed (hub deployment without it), emit `"Skipped coverage audit: tdd-refactor-coverage-audit skill not installed."` and continue.
**Report the three classes separately, and treat only two as gaps (#2865).** Since #2862 the conventions classify every test as `module`, `flow` or `contract`, and #2863 made the audit report them apart; the envelope's `classes` block carries all three. Summarize each, then list as gaps **only `module.unpaired` and `flow.undeclared`**.
**The other two cannot be gaps, by construction — state the reason, or the omission reads as arbitrary and the next edit adds a third bucket back.** A `contract` test pairs by **declared subject** and a `flow.declared` spec pairs by **annotation**; neither pairs by stem, so neither has an unpaired stem to report. Reading the flat pre-#2862 fields alone reports both as uncovered sources — correct, deliberate test design flagged as a coverage gap, at a volume that scales with the number of flow specs. **That is worse than a missing warning**: audit (3) is non-blocking so it can be read at a glance, and an advisory whose false positives grow with the codebase is one nobody reads, which removes the genuine `module.unpaired` findings along with the noise.
**`coverage` is a module-class ratio; `flow.undeclared` is a count.** Do not average them into one figure — a project with full module pairing and six orphaned flow specs is not 100% covered, and a single number says it is.
2a. **Audit (4) — announcement pairing (#2790).** Returned by the same `nonstop-audit.js` call as (1) and (2); no separate invocation. Reconciles the sender-side ledger for every processed sub-issue and reports, as **warnings**: a `work-completed` recorded with no `work-started` (`missingOpener` — the observed defect), an opener with no closer (`missingCloser`), and any announcement composed but left `pending` or recorded `failed` (`undispatched`).
   A composition that resolved `shouldSend: false` — no peers, a disabled group — is recorded `skipped` at composition time with the notice as its reason (#2990), and is reported as its own `skipped` count, **never** under `undispatched`: nothing was meant to be sent, and counting it there made the common case a false positive that buried the real omission. The count keeps an all-skipped run from falling silent, which would read like a ledger never written. Every composition path records through the same ledger call — `/work`, the review events, the `/done` push group and the branch-operation notices — so the record-only entries carry the same shape.
   **Advisory, never blocking** — it audits a channel that gates nothing, and an audit stricter than the thing it audits is a gate by the back door. `status: "skip"` means no ledger exists in this working directory: peer messaging may be disabled, or the run predates the ledger. **Skip is not a pass and not a failure** — nothing was recorded, so nothing can be reconciled, and reporting dropped openers there would train the reader to ignore the audit. Relay `caveats` verbatim: the ledger is project-scoped with no per-session form, so entries from two concurrent sessions cannot be separated after the fact and the audit says so rather than implying it isolated one run.
2b. **End-of-run sweep (#3202).** Under `--nonstop` Step 4f runs once, after the last sub-issue and before this audit. A failure is reported here as **blocking**, beside audit (2), with the attribution Step 4f produced (failing suites and tests, the sub-issues whose changed files they cover, or `unattributed`); processed sub-issues stay `in_review`.
3. Aggregate audit output. Proceed to the epic `in_review` move only after audit (2) blocks and an end-of-run sweep failure are cleared. The others clear nothing: (1) commit density is a warning, (3) test coverage is advisory, (4) announcement pairing is a warning, (5) doc judgment is a warning, and (6) a missing Review-State Gate decision is a warning.
4. **A `--concurrent` run is audited exactly as a sequential one (#3139).** Every member fired its gates and events once and carries its own `Refs #N` set, so audits (1), (2) and (4) read the ledger and commits without a concurrent-specific path. Two things the summary adds: the leftover-worktree report repeated from each group's check (`leftoverWorktrees()`, #3132), and — when `--no-review` was passed, or the `diff-review` skill was absent — the Tier 3 skips named per member, so a run whose merges rested on Tiers 1–2 alone is distinguishable from one independently reviewed. A member that halted keeps its worktree; the audit names it rather than counting it processed.
